## Critical Issues

### CR-01: Bump `package.json` version to 2.0.0 before the first renamed publish

**File:** `package.json:3`
**Issue:** The manifest still reads `"version": "1.6.1"`, but D-03 and this phase's own release checklist require the first release under the new name to be `2.0.0` (`.planning/phases/17.1-full-project-rename/17.1-RELEASE-CHECKLIST.md:30` — "## 3. `npm publish` `@shipwithai/loopnote@2.0.0`"). The published version is derived *only* from this field: `scripts/release-identity.mjs:13` (`export const version = manifest.version;`) feeds `packageLabel`, `archiveBasename` (line 18), `registryTarballUrl`, `packumentUrl`, `provenanceSubject`, and the `--github-env` emission of `LOOPNOTE_RELEASE_VERSION`/`LOOPNOTE_RELEASE_ARCHIVE_BASENAME` (line 29) consumed by `.github/workflows/publish-npm.yml:99,107,165,203`. Nothing in the repo and no checklist item bumps it — item 2 covers the renamed CI variable/secret and item 3 jumps straight to publishing. Running the pipeline as documented therefore publishes `@shipwithai/loopnote@1.6.1`, which (a) contradicts D-03's "the v2.0 milestone ships once, renamed, as 2.0.0", and (b) makes the marketplace skill's prerequisite `>=2.0.0 <3.0.0` and its install guidance `@shipwithai/loopnote@2.0.0` unsatisfiable, blocking checklist item 8 (`17.1-RELEASE-CHECKLIST.md:62`). npm publishes are effectively irreversible, so this must be fixed before the release run, not after.
**Fix:**
```json
{
  "name": "@shipwithai/loopnote",
  "version": "2.0.0",
```

## Warnings

### WR-01: Create the migrated support state with 0o600 instead of inheriting the legacy file's mode

**File:** `src/server/support-store.ts:147-148`
**Issue:** The new D-06 one-time copy propagates the legacy file's permission bits to the brand-new state file:
```ts
      const mode = (await fileSystem.stat(legacyPath)).mode & 0o777;
      await writeAtomic(bytes, mode);
```
`writeAtomic` both opens with that mode and then force-`chmod`s to it (`support-store.ts:121-122`), so umask cannot narrow it. Every other write in this module hardcodes private modes — `persist` uses `0o600` (line 133) and the directory is `0o700` (line 118) — precisely because `support.json` holds the `installationId` that the support verification flow treats as the install's identity. If the legacy `Cumpa`/`cumpa` `support.json` is group- or world-accessible (restored from a `tar` without `-p`, copied by a sync/backup tool, moved between machines, or hand-edited), the new `.../Loopnote/support.json` is created with those same bits. Because `state()` only writes when the file is *absent* (`support-store.ts:161-172`), the weak mode then persists for the life of the install: a local co-user can read the installation identity, and with a writable mode can set `status: "verified"`. Mode preservation buys nothing here — the destination is a new path that no one else has ever referenced.
**Fix:**
```ts
      const bytes = await fileSystem.readFile(legacyPath);
      SupportStateV1Schema.parse(JSON.parse(bytes.toString('utf8')));
      await writeAtomic(bytes, 0o600);
```
(`stat`/`chmod` can then come back out of `SupportFileSystem` at `support-store.ts:35,38,47,52` if nothing else needs them.)

### WR-02: The documented `mv .cumpa .loopnote` upgrade path silently recovers nothing

**File:** `src/domain/comparison-key.ts:5-8`
**Issue:** The four hash domain-separation tags were renamed:
```ts
const DOMAIN = Buffer.from(`${RENAME_MAP.slug}-comparison-key-v1`, 'utf8');
const RANGE_DOMAIN = Buffer.from(`${RENAME_MAP.slug}-range-review-key-v1`, 'utf8');
const UNCOMMITTED_DOMAIN = Buffer.from(`${RENAME_MAP.slug}-uncommitted-review-key-v1`, 'utf8');
const STANDALONE_DOMAIN = Buffer.from(`${RENAME_MAP.slug}-standalone-review-key-v1`, 'utf8');
```
Draft files are named by that hash — `src/server/draft-loader.ts:118` computes `comparisonKey(comparison.baseCommitOid, comparison.headCommitOid)` and line 120 builds `${draftsDirectory}/${key}.json`. For an unchanged base/head pair the key is now a different 64-hex string, so D-05's prescribed recovery ("Document a manual `mv .cumpa .<new>` in the README/upgrade notes") produces a directory full of files the new code never looks up, with no error and no warning — the user is told their drafts are portable and silently gets an empty review. `src/domain/anchor.ts:50-51` compounds it: even a hand-renamed draft would report every stored comment as `anchor-mismatch`, because `CONTEXT_DOMAIN`/`UNIQUE_DOMAIN` changed too. The in-document `reviewKey` compared at `src/server/draft-loader.ts:65,76,94` mismatches for the same reason. Separately, the D-05-mandated note was never written: `git grep '\.cumpa' -- README.md docs/ PRODUCT.md DESIGN.md` returns nothing. Abandoning `.cumpa/` is a deliberate decision; advertising a `mv` that cannot work is not.
**Fix:** Pick one. Either keep the four domain tags at their `cumpa-*-v1` values — they are internal domain-separation constants, never user-visible, and the audit already has an exception category for exactly this class of literal — which makes `mv .cumpa .loopnote` actually restore drafts; or drop the `mv` guidance and state plainly in the upgrade notes that 1.x drafts and exports are not readable by 2.0.0. Do not ship the current combination.

### WR-03: Scope the rename gate's two unscoped exemptions

**File:** `scripts/audit-rename-exceptions.mjs:107-111`
**Issue:** Two of the four allow-list categories are not file-scoped, so the phase's final gate is structurally blind:
```js
  if (OLD_KIND_LITERAL_PATTERN.test(line)) return true;
  if (MIGRATION_PATH_FILES.has(file) && SUPPORT_JSON_PATTERN.test(line)) return true;
  if (EXCLUSION_PREFIX_FILES.has(file) && EXCLUSION_PREFIX_PATTERN.test(line)) return true;
  if (HISTORICAL_IDENTITY_FILES.has(file) && HISTORICAL_IDENTITY_PATTERN.test(line)) return true;
  if (file === HISTORICAL_REAL_RUNTIME_FILE) return true;
```
Line 111 exempts **an entire file** with no pattern at all, so any present or future `cumpa` string in `tests/helpers/public-runtime.ts` is invisible to the gate. Its 13 current hits are legitimately the still-published `@shipwithai/cumpa@1.5.0` identity, but checklist item 3 flips that helper to the renamed package once 2.0.0 is live, and from then on the exemption permanently masks anything left behind there. Line 107 has the narrower version of the same problem: `OLD_KIND_LITERAL_PATTERN` (line 32) is matched against every line of every file, so a single line containing both a legitimate `cumpa.review-request` literal *and* a real leftover is waved through. The other three categories already demonstrate the correct shape.
**Fix:**
```js
const OLD_KIND_LITERAL_FILES = new Set(['src/cli/request.ts', 'tests/cli/request.test.ts', 'tests/unit/agent-request.test.ts']);
const HISTORICAL_REAL_RUNTIME_FILE = 'tests/helpers/public-runtime.ts';
const HISTORICAL_REAL_RUNTIME_PATTERN = /@shipwithai\/cumpa|dist\/bin\/cumpa\.mjs|['"`]cumpa(?:\.cmd)?['"`]|Cumpa\b/u;

function isAllowedException(file, line) {
  if (OLD_KIND_LITERAL_FILES.has(file) && OLD_KIND_LITERAL_PATTERN.test(line)) return true;
  if (MIGRATION_PATH_FILES.has(file) && SUPPORT_JSON_PATTERN.test(line)) return true;
  if (EXCLUSION_PREFIX_FILES.has(file) && EXCLUSION_PREFIX_PATTERN.test(line)) return true;
  if (HISTORICAL_IDENTITY_FILES.has(file) && HISTORICAL_IDENTITY_PATTERN.test(line)) return true;
  if (file === HISTORICAL_REAL_RUNTIME_FILE && HISTORICAL_REAL_RUNTIME_PATTERN.test(line)) return true;
  return false;
}
```

### IN-01: Give the rename audit a CLI entrypoint

**File:** `scripts/audit-rename-exceptions.mjs:144`
**Issue:** The module ends at `export default auditRenameExceptions;` with no `main`, so `node scripts/audit-rename-exceptions.mjs` prints nothing and exits 0 — confirmed by running it. Every sibling gate in `scripts/` is runnable standalone (`scripts/release-identity.mjs:45` guards with `if (import.meta.main) main(...)`; `verify-prerequisites.mjs`, `verify-production-artifacts.mjs`, `verify-npm-release.mjs`, `verify-supabase-support.mjs` all have entrypoints and their own `npm run verify:*` scripts). The gate is therefore reachable only through `tests/unit/rename-audit.test.ts`, and the `"test": "vitest run"` script added to `package.json:36` in this phase is referenced by neither workflow (`git grep -E 'npm (run )?test' -- .github/` → no matches), so nothing in CI runs it.
**Fix:**
```js
export default auditRenameExceptions;

if (import.meta.main) {
  const hits = auditRenameExceptions();
  for (const hit of hits) process.stderr.write(`${hit.file}:${hit.line}: ${hit.text}\n`);
  if (hits.length > 0) {
    process.stderr.write(`${hits.length} disallowed legacy-name hit(s)\n`);
    process.exitCode = 1;
  }
}
```
