# Phase 17.1 — Manual Release Checklist (Cumpa → Loopnote)

**Status:** All items below are manual. None are automated by this phase (D-02, D-08, D-09). Nothing in `.planning/phases/17.1-full-project-rename/` executes a GitHub, npm, Supabase, or Stripe operation on live infrastructure — this document only records, in dependency order, the steps the maintainer runs by hand before and during the v2.0.0 release.

**Prerequisite — local repo state:** Before starting this checklist, push `main`. As of this writing the local `main` branch in `~/projects/diff-review` is roughly 300 commits ahead of `origin/main` (Phase 17.1's full rename work, committed locally per sequential-executor convention). None of the steps below — especially the `npm publish`/CI steps in Item 3, which run off the pushed `main` — can happen until that push lands. Pushing `main` is itself a live, credentialed git operation and is therefore also manual.

---

## 1. GitHub repo rename

Rename the GitHub repository from `Ship-With-AI/cumpa` to `Ship-With-AI/loopnote` (GitHub dashboard: Settings → General → Repository name). GitHub automatically keeps HTTP(S) redirects from the old name to the new one for web/clone/fetch traffic.

- **`git remote` reminder:** GitHub's redirect does **not** update an already-cloned repository's stored remote URL. After the GitHub-side rename, every maintainer with an existing local clone (including this `~/projects/diff-review` checkout) must run:
  ```sh
  git remote set-url origin https://github.com/Ship-With-AI/loopnote.git
  ```
  (or the equivalent `git@github.com:Ship-With-AI/loopnote.git` for an SSH remote). Relying on the redirect indefinitely is not safe — GitHub's redirect can be superseded if the old name is ever reused by a different repository.
- **`package.json` cross-reference:** `package.json`'s `repository.url` (`git+https://github.com/Ship-With-AI/loopnote.git`) and `bugs.url` (`https://github.com/Ship-With-AI/loopnote/issues`) are **already updated in code** by plan 17.1-03 — no further edit is needed there. (This project's `package.json` has no `homepage` field, so there is nothing to update on that key.) This checklist item covers only the GitHub-side rename and the local `git remote set-url`, not re-editing `package.json`.
- The local folder `~/projects/diff-review` itself is **not** renamed (per D-09) — only the GitHub repository and remote URL.

## 2. Re-create renamed GitHub Actions repo variable/secret

In the (renamed) GitHub repository's Settings → Secrets and variables → Actions, re-create, under their **new** names:

- Repository **variable** `LOOPNOTE_RELEASE_SOURCE_SHA` (Variables tab) — read by `.github/workflows/publish-npm.yml`'s candidate-authorization check (`vars.LOOPNOTE_RELEASE_SOURCE_SHA`, compared against `GITHUB_SHA` before any checkout).
- Repository **secret** `LOOPNOTE_RELEASE_BUILD_ORIGIN` (Secrets tab) — read by the same workflow (`secrets.LOOPNOTE_RELEASE_BUILD_ORIGIN`), the canonical support-service origin injected into the producer/scanner/acceptance steps as `LOOPNOTE_RELEASE_SUPPORT_SERVICE_URL`.

Both previously existed under the old names `CUMPA_RELEASE_SOURCE_SHA` / `CUMPA_RELEASE_BUILD_ORIGIN`. The workflow YAML was renamed in code by plan 17.1-05 and now references **only** the new names — the stable-publish job's authorization-check step fails until both exist under their new names. Use the same values as the old entries (copy, do not change values); do not delete the old `CUMPA_*` entries until the new ones are confirmed working, in case of rollback.

### Pre-publish version check

`package.json`'s `version` field was already bumped to `2.0.0` in Phase 17.1's gap-closure plan 17.1-23 (per D-03) — this item requires NO separate `npm version` bump. Before running the publish workflow, verify `package.json`'s `version` reads exactly `2.0.0` (e.g. `node -p "require('./package.json').version"`) and that `package-lock.json`'s matching `version` fields agree; if either has drifted from `2.0.0`, stop and investigate rather than re-running `npm version`.

## 3. `npm publish` `@shipwithai/loopnote@2.0.0`

Publish the first release under the new name. Per D-03, there is **no** `1.7.0` under the old name — the v2.0 milestone ships exactly once, already renamed, as `2.0.0`. Follow the existing CI-built, byte-bound-inspection, attested stable-publish pipeline described in `docs/distribution-operations.md` (Phase 5 — unchanged mechanics: fresh CI build, actual-byte inspection/approval, unchanged-byte publication in the same workflow run/attempt, trusted-publisher OIDC via `.github/workflows/publish-npm.yml`'s `npm-release` job). This step requires `main` to be pushed (see Prerequisite above) and Item 2's GitHub Actions variable/secret to already exist.

## 4. `npm deprecate @shipwithai/cumpa`

Only after Item 3's `@shipwithai/loopnote@2.0.0` is live on the registry, run:
```sh
npm deprecate @shipwithai/cumpa "Cumpa has been renamed to Loopnote. Install @shipwithai/loopnote instead: https://www.npmjs.com/package/@shipwithai/loopnote"
```
Per D-02, this is deprecation only — **no alias, no forwarding `cumpa` bin, no shim code**. This requires maintainer npm credentials with publish rights on the old `@shipwithai/cumpa` package.

## 5. Rename the live Supabase project

In the Supabase dashboard, rename the live project's display name from "Cumpa" to "Loopnote" (Settings → General), matching `supabase/config.toml`'s `project_id = "loopnote"` (already renamed in code by plan 17.1-09). The GitHub Actions `SUPABASE_PROJECT_REF` variable holds an opaque project ref, not a product-named string, and does **not** need to change.

Regarding deployed Edge Function secrets: as of this writing, none of the three deployed functions (`stripe-webhook`, `support-api`, `support-flow`) read a `CUMPA_*`- or `LOOPNOTE_*`-prefixed secret — they read only `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_ID`, `SUPABASE_URL`, and `SUPABASE_SERVICE_ROLE_KEY` (all already generic, non-product-named). **No deployed function secret currently requires renaming.** If a future deploy introduces a product-named secret, rename it here before deploying.

## 6. Rename the Stripe product display name

In the Stripe dashboard (Products), rename the product backing `STRIPE_PRICE_ID` from its Cumpa-branded display name to "Loopnote" (or the equivalent new support-product name). Per `docs/support-service-operations.md`'s price-stability invariant, the Price's unit amount (USD 49.99) **must not change** — only the product/price display name and description shown to supporters.

## 7. Update AIOS/library listing pages

Update any third-party AI-tool directories, skill marketplaces, or library listing pages that reference the old `@shipwithai/cumpa` package name or the "Cumpa" display name, pointing them at `@shipwithai/loopnote` and "Loopnote" instead.

## 8. Merge the marketplace skill PR (final item)

Merge the marketplace skill draft PR in `Ship-With-AI/skills`, branch `cumpa-uncommitted-files-request-modes`. Plan 17.1-21 (Task 2) already renamed that branch's `skills/cumpa/` tree to `skills/loopnote/` locally (`SKILL.md`, `scripts/check-loopnote.mjs`, install guidance, `kind` literals, invocation examples) and confirmed its version prerequisite reads `>=2.0.0 <3.0.0` — committed locally, **not pushed**. Before merging:

1. Push the renamed branch to `Ship-With-AI/skills`.
2. Open/update the pull request.
3. **Do not merge until Item 3 above (`npm publish @shipwithai/loopnote@2.0.0`) has landed** — the skill's `SKILL.md`/`check-loopnote.mjs` prerequisite (`>=2.0.0 <3.0.0`) and install guidance (`npm install --global @shipwithai/loopnote@2.0.0`) are only satisfiable once that release exists on the registry.

This is the last item in the checklist: every prior step (repo rename, CI secrets, npm release/deprecation, Supabase/Stripe renames, listing updates) is a precondition for this merge landing cleanly.
