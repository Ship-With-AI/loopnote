### Warnings

#### WR-01: Anchor Category 5 to the upgrade-section literals instead of the bare product name

**File:** `scripts/audit-rename-exceptions.mjs:88-89` (applied at `:121`)

**Issue:** `UPGRADE_NOTES_PATTERN = /\.cumpa\/|\bCumpa\b/u` exempts every line of `README.md` that contains the standalone word `Cumpa`, not only the new upgrade section. The comment at `:85-87` claims the category is "a narrow literal pattern" that "cannot mask a genuinely new leftover `cumpa` reference" — true for other files (the file scope is the exact string `README.md`, so `docs/**` and nested READMEs stay covered), but inside `README.md` the gate no longer detects the old product name at all. That is exactly the token REN-01's audit exists to catch, in the repository's most leftover-prone, user-facing document: a future edit reintroducing e.g. "Cumpa reviews regular UTF-8 text files only" into the intro would pass `npm test`'s rename audit (`tests/unit/rename-audit.test.ts:11-18`) silently. The sibling categories all pair a file scope with a genuinely narrow literal — Category 2 requires the line to also name `support.json` (`:52-54`), Category 3 requires `cumpaPath`/`cumpaish`/`.cumpa` (`:59`), Category 4 requires a version-pinned package identity (`:73`) — so Category 5 is the only one whose pattern is the product name itself. Both currently exempt lines are matched by narrower literals already present in the text (`README.md:280` is the heading, `README.md:282` contains `.cumpa/` and "renamed continuation of Cumpa"), so tightening costs nothing.

**Fix:**
```javascript
const UPGRADE_NOTES_FILE = 'README.md';
const UPGRADE_NOTES_PATTERN = /\.cumpa\/|## Upgrading from Cumpa|renamed continuation of Cumpa/u;
```
