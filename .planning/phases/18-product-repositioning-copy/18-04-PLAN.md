<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| `comparison.repositoryRoot`/`grounded.repositoryRoot`/`scope.repositoryRoot` (already-validated, repository-local paths) to the new `repoName` field, rendered as plain text in `document.title` | Server computes `path.basename()` of a path the server itself already resolved and validated when the session was created; no new untrusted input enters here |
| `session.value?.repoName` to `document.title` (Vue reactive binding, not `innerHTML`) | `document.title` assignment is a plain string property set, not a DOM-injection sink; no HTML parsing occurs |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-18-04-01 | Tampering | `repoName` computed via `path.basename()` on an already-resolved, already-validated `repositoryRoot` at all four `SessionResponseSchema.parse` call sites | accept | `repositoryRoot` is never attacker-controlled free text at this point in the request lifecycle — it is the server's own resolved repository root, established before any capability registry is created; `basename()` can only return a path segment already present in that trusted value. |
| T-18-04-02 | Information Disclosure | `repoName` (a folder basename) now visible in `document.title` and the session response JSON | accept | The repository's folder name is already visible to the local user running the CLI in that directory; this is loopback-only, single-developer tooling (per PRODUCT.md), not new exposure to any other party. |
| T-18-04-03 | Tampering (XSS) | `document.title` assignment sourced from `session.value?.repoName` | mitigate | `document.title` is a plain string property, not `innerHTML`/`v-html` — browsers never parse its value as markup; no new Vue template uses `v-html` for this data. |
</threat_model>
