<objective>
Prove, empirically and in a real Monaco editor (not by source review), whether interactive thread chrome (buttons, a textarea, Tab/Shift+Tab focus cycling, Esc) layered over N simultaneous view zones can reliably receive pointer and keyboard input, keep paired Base/Head zone heights in sync, and survive scrolling and hidden-unchanged-region collapse/expand — then measure input-to-paint lag at 30 threads. This is the go/no-go gate for the entire phase (THREAD-01..09): CONTEXT.md and ROADMAP.md both require this decision before any production thread UI is built.

Purpose: `diff-adapter.ts` today proves exactly one view-zone pair works (the single unsaved-draft composer). RESEARCH.md identifies a documented Monaco bug where content widgets positioned `BELOW` an anchor line go blank once the zone is partially scrolled out of the viewport, with `IOverlayWidget` + `onDomNodeTop` as the candidate workaround carrying its own reported scroll-jank risk. Neither claim is verified against this project's own Monaco version, fonts, or `hideUnchangedRegions` configuration — only a real measurement resolves it.
Output: A recorded go/no-go decision (and, if "go", which widget technique) that Plan 23-05 will build the production keyed multi-zone adapter against. No production code changes.
</objective>
