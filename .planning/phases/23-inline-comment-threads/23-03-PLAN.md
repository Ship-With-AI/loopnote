<feature>
  <name>Keyed thread-zone diff classifier</name>
  <files>src/web/model/thread-zone-diff.ts, tests/unit/thread-zone-diff.test.ts</files>
  <behavior>
Export `diffThreadIds(previous: ReadonlySet<string>, next: readonly WorkspaceComment[]): Readonly<{ toCreate: readonly string[]; toRemove: readonly string[]; toKeep: readonly string[] }>`, the exact shape RESEARCH.md Pattern 3 specifies: ids in `next` not in `previous` → `toCreate`; ids in `previous` not in `next` → `toRemove`; ids in both → `toKeep`. No Monaco/Vue import — this is consumed by Plan 23-07's DiffWorkspace.vue mounting loop, which owns the actual zone/widget create-or-remove calls per id.

Cases:
- `previous` empty, `next` has 2 comments → both ids in `toCreate`, `toRemove` and `toKeep` empty.
- `previous` has 2 ids, `next` is empty → both in `toRemove`.
- `previous` and `next` share one id, `next` additionally has one new id → shared id in `toKeep`, new id in `toCreate`, nothing in `toRemove`.
- `previous` has an id not present in `next` and `next` has a different new id → the stale id in `toRemove`, the new id in `toCreate`, neither in `toKeep`.
- `previous` and `next` are identical sets → everything in `toKeep`, both other arrays empty.
- `next` contains a comment whose `id` repeats (same id object different reference) → appears exactly once across the three output arrays (classifier is set-based, not array-length-based).
  </behavior>
  <implementation>
Build `nextIds = new Set(next.map((c) => c.id))` once; derive the three arrays from set membership, mirroring the shape already given in RESEARCH.md's Code Examples section (do not re-derive a different shape — Plan 23-07 is written against exactly this `{ toCreate, toRemove, toKeep }` field naming).
  </implementation>
</feature>

<feature>
  <name>Orphaned-comment grouping projection</name>
  <files>src/web/model/orphaned-comments.ts, tests/unit/orphaned-comments.test.ts, src/web/model/comment-groups.ts</files>
  <behavior>
In `comment-groups.ts`, add the `export` keyword to the existing `orderPathIdentity` (line 32) and `orderText` (line 43) functions — mechanical, zero behavior change (same pattern as the project's prior "gained only the export keyword" precedent) — so the new module can reuse the same byte-order tiebreak instead of re-deriving it.

In new `src/web/model/orphaned-comments.ts`, export `projectOrphanedCommentGroup(comments: readonly WorkspaceComment[]): readonly Readonly<{ path: RecordedAnchorDetails['path']; comments: readonly WorkspaceComment[] }>[]`: filter to `comment.status === 'orphaned'`, group by `comment.recordedAnchor.path.bytesBase64url`, sort the groups by `orderPathIdentity` (imported from `comment-groups.ts`), and within each group sort by `(side: base-before-head, line, createdAt, id)` — the same tiebreak shape as `comment-groups.ts`'s `orderComments` (lines 52-58), reimplemented locally since `WorkspaceComment`'s field names differ slightly from `ReviewCommentProjection` (no shared type to import a function against).

Cases:
- Empty input → `[]`.
- All comments `status: 'verified'` → `[]` (nothing orphaned).
- Two orphaned comments with different `recordedAnchor.path` → two groups, ordered by `orderPathIdentity`.
- Two orphaned comments sharing one `recordedAnchor.path`, one `side: 'base'` one `side: 'head'`, same line → base before head within the one group.
- A mix of `'verified'`, `'stale'`, and `'orphaned'` comments → only the orphaned ones appear in any group.
  </behavior>
  <implementation>
Follow `comment-groups.ts`'s `groupsForState` (lines 60-86) structurally: build a `Map<string, { path; comments: WorkspaceComment[] }>` in one pass, then sort entries and inner arrays. This file does not need an "inventory order" parameter (unlike `groupsForState`) since orphaned comments' recorded paths, by definition, do not correspond to any currently-resolvable file in the session's inventory — byte order alone is the only meaningful cross-session-stable order.
  </implementation>
</feature>
