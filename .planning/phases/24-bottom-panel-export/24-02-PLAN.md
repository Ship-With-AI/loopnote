  <behavior>
Export a pure module with no Monaco/Vue import:

```ts
export type CommentsTabBucket = 'open' | 'stale' | 'resolved';
export type CommentsTabRow = Readonly<{ comment: WorkspaceComment; bucket: CommentsTabBucket }>;
export type CommentsTabFileGroup = Readonly<{ leaf: VisibleFileTreeLeaf; rows: readonly CommentsTabRow[] }>;
export function projectCommentsTabFileGroups(
  comments: readonly WorkspaceComment[],
  flatFileRows: readonly VisibleFileTreeLeaf[],
): readonly CommentsTabFileGroup[];
```

`CommentsTabFileGroup` carries the whole `leaf: VisibleFileTreeLeaf` (not a bare `fileId`/`display` pair) so `CommentsTab.vue` can reuse the same `leaf.file.newPath?.display ?? leaf.file.oldPath?.display` resolution `fileTypeMarkFor()` (Plan 24-01) and `PathText.vue` already expect, without this module inventing a second path-display convention.

Bucket assignment per comment (UI-SPEC's "resolved wins" rule, verbatim): `comment.state === 'resolved' ? 'resolved' : comment.status === 'stale' ? 'stale' : 'open'` — a resolved comment buckets to `'resolved'` regardless of its `status` (even `'stale'` or `'orphaned'`... though orphaned comments are excluded before bucket assignment, see below); a non-resolved comment with `status === 'stale'` buckets to `'stale'`; everything else (open + `status === 'verified'`) buckets to `'open'`.

Exclusion (both independent, applied before grouping): a comment with `status === 'orphaned'` is excluded ("can never match a live fileId by definition", UI-SPEC verbatim — these are Phase 23's `projectOrphanedCommentGroup()`'s job, called directly by `CommentsTab.vue`, not re-derived here); a comment whose `fileId` is `null`, or whose `fileId` has no matching entry in `flatFileRows` (filtered out of the visible tree), is also excluded.

Outer order: build `const fileOrder = new Map(flatFileRows.map((row, index) => [row.fileId, index]));` once (never `indexOf` scans), then sort file groups by that index ascending — mirrors `comment-groups.ts`'s `groupsForState`'s `inventoryOrder` map and `thread-order.ts`'s planned identical idiom (`24-PATTERNS.md`). A file present in `flatFileRows` with zero matching (non-excluded) comments produces **no** group entry at all — never an empty group.

Inner order within a group: sort by `(bucketRank, line, comment.id)` ascending, where `bucketRank = { open: 0, stale: 1, resolved: 2 }` — line ascending within a bucket (UI-SPEC verbatim), `comment.id` as a final lexicographic tie-break for determinism (no side-level tie-break is specified by UI-SPEC for this list, unlike `comment-groups.ts`'s `orderComments`).

Cases (write as `expect(...).toEqual(...)`/`toBe(...)` before implementing):
- Empty `comments` and/or empty `flatFileRows` → `[]`.
- A single comment with `state: 'open', status: 'verified'` in a file present in `flatFileRows` → one group for that file, one row with `bucket: 'open'`.
- Three comments in the same file — one `state:'open',status:'verified'`, one `state:'open',status:'stale'`, one `state:'resolved',status:'verified'` — inserted in resolved/stale/open input order → the returned group's `rows` are ordered open, stale, resolved (bucket order wins over input order).
- A comment with `state:'resolved', status:'stale'` buckets to `'resolved'`, not `'stale'` ("resolved wins").
- Two comments in the same bucket, same file, different lines → ordered by line ascending.
- Two files, where the file appearing later in `flatFileRows` happens to have comments with lower line numbers than the file appearing earlier → group order follows `flatFileRows` index, never line number (cross-file ordering is strictly tree-path order).
- A comment with `status: 'orphaned'` is excluded from every group even when its `fileId` is non-null and matches a `flatFileRows` entry.
- A comment with `fileId: null` is excluded.
- A comment whose `fileId` has no matching entry in `flatFileRows` is excluded.
- A file present in `flatFileRows` with only excluded comments (orphaned, or `fileId` mismatched) produces no group for that file at all.
