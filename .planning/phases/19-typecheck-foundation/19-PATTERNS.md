### `src/web/components/DiffWorkspace.vue` (component, event-driven) — `TS2345`×6, `TS18048`×4, `TS2322`×1 (11 errors total, largest bucket)

**Analog:** the file's own `renderAnnotation()` (lines 146-193, contains the named error at line 172) versus its sibling resize-callback function around line 376-377 — the fix pattern already exists one function away in the same file.

**Error-producing code (DiffWorkspace.vue:146-172, verbatim):**
```ts
function renderAnnotation(): void {
  const zone = host.value?.querySelector<HTMLElement>('.monaco-anchor-zone--composer');
  const anchor = adapter?.getActiveAnchor();
  if (zone === undefined || anchor === undefined || anchor.fileId !== props.content.fileId) {
    unmountZone();
    return;
  }
  if (zoneRoot !== zone) {
    unmountZone();
    zoneRoot = zone;
  }
  const comment = currentComment();
  if (comment !== undefined) {
    render(h('section', { class: 'conversation-card inline-accepted-comment', 'data-comment-id': comment.id }, [
      /* ... vnode tree ... */
    ]), zone);   // ← line 172: TS2345 here
```
**Root cause:** `host.value?.querySelector<HTMLElement>(...)` returns `HTMLElement | null | undefined`. The guard at line 149 (`zone === undefined`) only eliminates `undefined`; `zone`'s narrowed type after that guard is still `HTMLElement | null`. Vue's `render(vnode, container)` second parameter is typed `Element | ShadowRoot` (no `null`), hence `TS2345` at every call site using `zone` in this function (lines 172, 179, 193, plus the `resizeAnchorZoneToContent(zone)` call at line 174).

**In-file precedent for the correct narrowing (DiffWorkspace.vue:376-377, already correct, zero errors):**
```ts
const zone = host.value?.querySelector<HTMLElement>('.monaco-anchor-zone--composer');
if (zone === null) return;
```
This sibling function guards on `zone === null` (not `=== undefined`), which is the half of the union `renderAnnotation()` is missing. **Fix pattern:** change line 149's condition to exclude both `null` and `undefined` explicitly (matching the codebase's consistent strict-equality style — no loose `== null` anywhere in `src/web`), e.g. `if (zone === null || zone === undefined || anchor === undefined || ...)`.

**Also declared in this file (zoneRoot/module-scope var, line 61):**
```ts
let zoneRoot: HTMLElement | undefined;
```
Note `zoneRoot` is typed `HTMLElement | undefined` (no `null`) — only the local `zone` returned by `querySelector` carries the `null` branch that needs the extra guard.

### `src/web/App.vue` (component, request-response/orchestration) — `TS2719`×1 (duplicate-type-identity), `TS2322`×2, `TS18048`×2 (5 errors total)

**Analog:** `src/web/components/ReviewNotesDialog.vue` — the prop-consumer side of the exact same type, independently redeclared.

**Declaration #1 — App.vue:76 (producer side):**
```ts
type AttachedLifecycle = 'ordinary' | 'waiting' | 'waitingDisconnected' | 'finishing' | 'completed' | 'retryableFailure' | 'terminalFailure';
```
used at App.vue:111:
```ts
const attachedLifecycle = ref<AttachedLifecycle>('ordinary');
```
and passed to the child at App.vue:1443 (the exact error line):
```html
:attached-lifecycle="isAttachedSession ? attachedLifecycle : undefined"
```

**Declaration #2 — ReviewNotesDialog.vue:20-26 (consumer side, independently declared, structurally narrower):**
```ts
type AttachedLifecycle =
  | 'waiting'
  | 'waitingDisconnected'
  | 'finishing'
  | 'completed'
  | 'retryableFailure'
  | 'terminalFailure';
```
used in the prop type at ReviewNotesDialog.vue:48:
```ts
readonly attachedLifecycle?: AttachedLifecycle;
```

**Root cause (`TS2719`):** two locally-scoped `type AttachedLifecycle = ...` declarations with overlapping-but-not-identical literal members (App.vue's includes `'ordinary'`; ReviewNotesDialog.vue's does not — App.vue only ever passes `attachedLifecycle` to this prop when `isAttachedSession` is true, at which point `'ordinary'` cannot occur, but the types remain nominally distinct literal unions to TS). Each is a private `type` alias local to its own `<script setup>` block, so TS treats them as unrelated even though their overlapping members read identically — classic "two different types with this name exist, but they are unrelated."

**Fix pattern (per RESEARCH.md § Open Questions, recommendation accepted):** consolidate into a single exported type and import it in both files — do not re-declare locally in either file. Confirmed **not** anchor-identity code (`PITFALLS.md` Critical Pitfall 4 guard does not apply; `AttachedLifecycle` lives in the attached/agent-lifecycle domain, unrelated to `src/domain/anchor.ts`). Suggested home: export from `ReviewNotesDialog.vue`'s module (it already defines the narrower, consumer-facing shape with `<script setup>` `type` export, matching the `UiIconName` export pattern in `UiIcon.vue:2` — `export type UiIconName = ...`) or hoist to a shared model file (e.g. alongside `ReadOnlyDraftLoad` in `src/web/model/review-draft-state.ts`) and import in both `App.vue` and `ReviewNotesDialog.vue`. Either approach removes the duplicate declaration; App.vue's ternary (`isAttachedSession ? attachedLifecycle : undefined`) already excludes `'ordinary'` from reaching the prop at runtime, so narrowing App.vue's own `attachedLifecycle` ref type is not required — only the duplicate alias needs removing.

**Remaining App.vue errors (`TS2322`×2, `TS18048`×2) — `session.value` possibly-undefined props, not individually pinpointed by RESEARCH.md one-liners but same root cause class.** In-file precedent for the correct narrowing idiom already used throughout this file (App.vue, representative lines):
```ts
// App.vue:158 — optional-chaining + undefined fallback (established idiom)
const pinnedSession = computed(() =>
  session.value !== undefined && 'base' in session.value ? session.value : undefined,
);
// App.vue:191 — optional chaining through to a leaf property
const supportEnabled = computed(() => session.value?.support?.enabled === true);
// App.vue:289 — optional chaining feeding a boolean computed
const isAttachedSession = computed(() => session.value?.attached?.kind === 'agent-review');
```
Apply the same `session.value !== undefined ? ... : ...` / `session.value?.x ?? default` idiom at whichever two prop-binding call sites the vue-tsc run flags (narrow before passing into a prop typed without `| undefined`, or widen the receiving prop type — CONTEXT.md leaves this to discretion as long as runtime is unchanged).

### `src/web/components/DraftRecovery.vue` (component, transform) — `TS2339`×2

**Analog:** the same file's own script-side discriminant narrowing (lines 35-43) versus its template branch (lines 140-143) that doesn't use the same technique.

**Type definition (`src/web/model/review-draft-state.ts:45-48`):**
```ts
export type ReadOnlyDraftLoad = Extract<
  DraftLoadResponse,
  { readonly kind: 'malformed' | 'schemaInvalid' | 'newerUnsupported' }
>;
```
**Full three-variant shape (`src/server/draft-loader.ts:29-32`, the source discriminated union `DraftLoadResponse` is derived from):**
```ts
| Readonly<{ readonly kind: 'current'; readonly path: string; readonly raw: Buffer; readonly draft: ReviewDraftV1 }>
| Readonly<{ readonly kind: 'malformed'; readonly path: string; readonly raw: Buffer; readonly fingerprint: string; readonly detail: Readonly<{ readonly message: string }> }>
| Readonly<{ readonly kind: 'schemaInvalid'; readonly path: string; readonly raw: Buffer; readonly fingerprint: string; readonly details: readonly DraftIssue[] }>
| Readonly<{ readonly kind: 'newerUnsupported'; readonly path: string; readonly raw: Buffer; readonly foundVersion: number; readonly supportedVersion: typeof CURRENT_DRAFT_SCHEMA_VERSION }>;
```
Only the `'newerUnsupported'` variant carries `foundVersion`/`supportedVersion`.

**Correct in-file precedent — script-side narrowing already does this right (DraftRecovery.vue:35-43):**
```ts
const isRecoverable = computed(() => props.load.kind === 'malformed' || props.load.kind === 'schemaInvalid');
const problem = computed(() => props.load.kind === 'malformed'
  ? 'Malformed JSON'
  : 'Draft data does not match supported schema');
const details = computed(() => props.load.kind === 'schemaInvalid'
  ? props.load.details
  : props.load.kind === 'malformed'
    ? [{ path: 'Draft data', message: props.load.detail.message }]
    : []);
```
Each ternary tests `props.load.kind === <literal>` directly, which TS narrows correctly.

**Error-producing template code (DraftRecovery.vue:129-143, the `v-else` branch that does NOT use direct discriminant narrowing):**
```html
<section v-else class="draft-recovery__card">
  <ReviewStateBadge class="draft-recovery__status" kind="disabled" label="Read only" />
  <InlineNotice
    class="draft-recovery__notice"
    :tone="isRecoverable ? 'warning' : 'error'"
    :role="isRecoverable ? 'note' : 'alert'"
  >
    <template v-if="isRecoverable">
      <h1 id="draft-recovery-heading">Local review draft needs recovery</h1>
      <p>{{ RENAME_MAP.displayName }} could not safely read this draft. The existing file has not been changed.</p>
    </template>
    <template v-else>
      <h1 id="draft-recovery-heading">This draft needs a newer {{ RENAME_MAP.displayName }}</h1>
      <p>Draft schema version {{ load.foundVersion }} is newer than supported version {{ load.supportedVersion }}. Upgrade {{ RENAME_MAP.displayName }} to open it. The file has not been changed.</p>
      <!-- ↑ line 142: TS2339 ×2 here — load.foundVersion / load.supportedVersion -->
    </template>
  </InlineNotice>
```
**Root cause:** the inner `v-else` at line 140 is the else-branch of `v-if="isRecoverable"` (line 136) — `isRecoverable` is a `Ref<boolean>` computed from `props.load.kind`, but vue-tsc's template type-narrowing cannot propagate "if `isRecoverable` is false, then `load.kind` must be `'newerUnsupported'`" across two different bindings; it only narrows on direct `load.kind === '<literal>'` checks in the template, same as the Vue component compiler's template-expression narrowing rules used correctly in `v-if="isRecoverable"` at line 136 itself (a plain ref check, which is fine) but not transitively onto `load`.

**Fix pattern:** change the inner template conditional to test the discriminant directly, e.g. `<template v-else-if="load.kind === 'newerUnsupported'">`, mirroring the exact style already used in the script-side computeds above (`props.load.kind === 'schemaInvalid'`/`'malformed'`) — matching the codebase's established per-variant direct-literal-check idiom rather than threading narrowing through an intermediate boolean ref.

### CI Contract Wiring (applies to: `.github/workflows/deploy-supabase-production.yml`, `package.json`)
**Source:** commit `a8dfcf9` + `scripts/verify-supabase-support.mjs:1733-1757` + `tests/e2e/support-payment.spec.ts:220-224`.

The `repository-gates` job's command set is **pinned verbatim in three separate locations**, not just the YAML file. Adding `- run: npm run typecheck:web` to the workflow without updating the other two breaks CI's own workflow-verifier test:

2. **`repository-gates`-scoped command set** (`scripts/verify-supabase-support.mjs:1749-1752`, a second, job-scoped `Set` built from `gates = workflow.slice(workflow.indexOf('repository-gates:'), workflow.indexOf('deploy-production:'))`):

3. **Mutation-coverage row** (`tests/e2e/support-payment.spec.ts:221`):
   ```ts

   ```

### Nullable-value narrowing idiom (applies to: `DiffWorkspace.vue`, `App.vue`, `DraftRecovery.vue`)
**Source:** `src/web/App.vue:158,191,289` (optional-chaining + explicit `!== undefined`/`?? default`); `DiffWorkspace.vue:376-377` (explicit `=== null` early return); `DraftRecovery.vue:35-43` (explicit `kind === '<literal>'` discriminant checks).

Codebase convention is **strict, explicit equality checks** (`=== undefined`, `=== null`, `!== undefined`, or `kind === '<literal>'` discriminant tests) — never loose `== null`/`!= null`. Every one of the four error-bearing files already uses this idiom correctly somewhere in the same file; the fix in each case is to apply the *same local idiom* at the specific line that is missing one half of a union check (either a `null` vs. `undefined` branch, or a direct discriminant test instead of routing through an unrelated boolean).

### `tone`/semantic-state → `UiIconName` lookup table (applies to: `ReviewNotesDialog.vue`)
**Source:** `src/web/components/InlineNotice.vue:22-34`, `src/web/components/ui/ReviewStateBadge.vue:23-30`.

Both existing consumers of `UiIconName` map a semantic/tone string (`'success'`, `'resolved'`, `'verified'`, etc.) to an *icon* name (`'check'`) through an explicit switch/lookup table — never pass the semantic string straight through as the icon name. Any future `UiIcon` usage should follow this same indirection rather than assuming tone names and icon names are interchangeable strings.
