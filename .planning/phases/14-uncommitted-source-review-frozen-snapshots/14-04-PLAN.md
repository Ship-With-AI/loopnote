<objective>
Build `src/git/worktree-inventory.ts`, the Staged/Unstaged/Working-tree file-set discovery module, as a structural sibling to `src/git/inventory.ts`'s `createChangedFileInventory` — one explicit `git diff` invocation per source kind (never a single function that special-cases "which side is live"), per RESEARCH.md Pattern 1 and D-08's "follow git exactly, verify with fixtures, no special-casing."

Purpose: this is the sole authority for "what changed" in an uncommitted session (WTREE-01..04). Everything downstream — snapshot capture (14-07), session file lists (14-08), the changed-files tree (existing Vue components, reused unmodified) — consumes this module's `ChangedFile[]` output.

Key design resolution (not fully specified by RESEARCH.md, resolved here for the executor): for **Staged**, both diff endpoints (the merge-base tree and the index) are real Git objects — reuse `classifyAvailability()` from `src/git/availability.ts` completely unchanged via `createObjectReader`, identical to how `inventory.ts`'s `createChangedFileInventory` already classifies committed comparisons. For **Unstaged** and **Working-tree**, the worktree-resident side is not a Git object; `git diff --raw`/`--numstat` still report it with an all-zero placeholder OID and `additions`/`deletions` of `null` for binary content (git performs its own binary detection even against the worktree) — reuse that signal plus `oldMode`/`newMode === '120000'/'160000'` (symlink/submodule, already filesystem-accurate in git's raw output) unchanged from `classifyAvailability`'s cascade, and add a worktree-side size/UTF-8 check via bounded `fs.readFile` only for the one side `classifyAvailability` cannot resolve via `ObjectReader`. Do not compute a synthetic blob OID at this layer — `ChangedFile.oldBlobOid`/`newBlobOid` keep git's own raw-diff-reported values (including the all-zero worktree-side placeholder); the synthetic Git-compatible digest for non-object-backed sides is `worktree-content.ts`'s job (14-05), computed when it already has the bytes in hand.

Output: `createWorktreeChangedFileInventory(options, dependencies): Promise<readonly ChangedFile[]>` for all three source kinds, fixture-verified against git's own output.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Current worktree filesystem → `ChangedFile[]` | This module reads file-set and metadata directly from the local worktree the CLI was launched in (D-04: current worktree only); it never resolves paths outside `repositoryRoot`, and it is the first Phase 14 module to read worktree-resident (non-object) bytes for classification purposes. |
| `.cumpa/` internal storage → review surface | `.cumpa/` holds Cumpa's own drafts/snapshots; it must never itself become reviewable content. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-04-01 | Information disclosure | `classifyWorktreeSideAvailability`'s bounded `fs.readFile` | mitigate | `lstat` first (never `stat`), reject non-regular-file results (symlinks already short-circuited earlier via the mode check, so this is defense in depth against a TOCTOU swap), cap read length at `MAX_INLINE_TEXT_BYTES` — identical discipline to `PatchSnapshot.worktreeEntry()`'s existing pattern. |
| T-14-04-02 | Information disclosure | Untracked-file `.cumpa/` leakage | mitigate | `isCumpaInternalPath` applied to the untracked `ls-files` union as defense in depth, in addition to `.gitignore`'s own `/.cumpa/` rule — per RESEARCH.md's STRIDE table, the filter must not rely solely on the repository's own gitignore configuration being correct (WTREE-04). |
| T-14-04-03 | Tampering | Path traversal via pathspecs | accept | `pathspecs` are passed through unchanged to `git diff`/`git ls-files`, identical to the existing `createChangedFileInventory`'s handling; Git's own pathspec resolution is the trust boundary here, not new code in this module. |
| T-14-04-SC | Tampering | npm/pip/cargo installs | accept | No package-manager install in this plan — native `git` CLI via the existing `createGitRunner`, `node:fs/promises` built-ins. |
</threat_model>
