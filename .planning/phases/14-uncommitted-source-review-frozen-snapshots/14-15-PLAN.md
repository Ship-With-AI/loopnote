<objective>
Build the server- and CLI-side half of D-19's relaunch-recovery offer, which was never built despite being a locked, user-confirmed decision: `findUncommittedDraftCandidate` (14-08) is correctly implemented and called at launch, but its result is only ever printed as a misleading CLI console line (`src/cli/run.ts:696-700`) that promises an offer the browser never makes. This plan threads the candidate into the running session instead of discarding it after printing, and adds the server capability that actually copies the prior draft's comments into the current draft on acceptance — the missing mechanics 14-16 (the client-side half, in a later wave) wires a browser offer onto.

`DraftRecovery.vue`'s existing "recover a draft" UX is **not** reused here: its props (`ReadOnlyDraftLoad`, `recoverDraft(expectedFingerprint)`, "Back up existing draft and start new") are purpose-built for a different feature — recovering from a malformed/schema-invalid/too-new draft file on disk — not D-19's "a different-content relaunch found an older draft for the same source+base" offer. Reusing it here would force D-19's semantics through the wrong props and copy; this plan builds the distinct, smaller surface D-19 actually needs (one capability, one route, one session-response flag), which 14-16 attaches a dismissible banner to, following the exact pattern 14-12 already established for the "changed during capture" session banner.

Purpose: make D-19's "offers recovery... accepting creates a new draft... comments copied and reclassified; the old draft is left untouched" literal wording true, closing a gap the verification report found structurally real but entirely unbuilt.

Output: `UncommittedSessionResponseSchema`'s `recoveryAvailable` flag and the new `UncommittedDraftRecoveryResultSchema`; `draft-store.ts`'s `loadUncommittedDraftCandidateComments`; `capabilities.ts`'s `recoverUncommittedDraft` capability; `routes.ts`'s `POST /api/uncommitted/recover-draft`; `run.ts`'s candidate threading into `createUncommittedSessionApp`'s options.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `POST /api/uncommitted/recover-draft` | Same loopback-bound, already-authenticated session request pattern every other mutating client call (`/api/refresh`, `/api/draft/mutations`) already uses — no new auth surface. |
| Server → a second on-disk draft file (the recovery candidate), outside the active session's own draft path | New read-only cross-draft file access, introduced by this plan. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-15-01 | Tampering | Copying another draft's comments into the current draft from a forged/crafted candidate file | mitigate | `loadUncommittedDraftCandidateComments` validates the candidate file through the same `ReviewDraftV1Schema` used for the user's own drafts; each copied comment is re-submitted through the existing `draftStore.mutate()`/`applyDraftMutation('addComment')` path, which re-validates `DurableAnchorV1Schema`/`CommentBodySchema` and rejects duplicate anchors — no raw bytes from the candidate file are trusted or written directly. |
| T-14-15-02 | Tampering | Accidentally mutating or deleting the prior draft file during recovery | mitigate | `loadUncommittedDraftCandidateComments` only ever calls `fs.readFile`, never opens the candidate path for writing; `recoverUncommittedDraft()` writes exclusively through `draftStore`, which targets the *current* session's own draft file — matching D-19's "old draft left untouched." |
| T-14-15-03 | Information disclosure | `recoveryAvailable`/the recover endpoint exposing the prior draft's path, reviewKey, or comment content before acceptance | accept | The session response exposes only a boolean (`recoveryAvailable: true`); the recover endpoint takes no client-supplied parameters identifying the candidate, and comment content is only ever copied into the user's own new draft (which they already own) once they explicitly accept. |
| T-14-15-SC | Tampering | npm/pip/cargo installs | accept | No package-manager install in this plan — server/CLI wiring over already-shipped draft-store/capability patterns. |
</threat_model>
