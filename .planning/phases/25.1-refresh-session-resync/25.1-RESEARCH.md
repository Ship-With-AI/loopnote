# Phase 25.1: Refresh Session Resync - Research

**Researched:** 2026-11-06
**Domain:** Internal bug-fix — Vue 3 reactive state resync + component emit-contract fix (no new tech)
**Confidence:** HIGH

## Summary

This is pure internal-codebase archaeology: a gap-closure phase in an existing TypeScript/Vue 3 app with no new dependencies. Both root causes are confirmed by direct code reading. `App.vue`'s `performRefresh()` (`src/web/App.vue:1401-1424`) calls `sessionClient.refreshWorktreeSnapshot()` and `sessionClient.getDraft()` but never calls `sessionClient.getSession()` again — the only `session.value = loaded` assignment in the entire file is the one-time mount call at `src/web/App.vue:1455-1456`, inside `onMounted`. Every computed that drives the tree (`flatFileRows:329`), navigation (`reviewableFiles:211`, `selectedIndex:284`), status bar (`sessionKindTitleSegment`-adjacent computeds around `264`), and identity pill/popover (passed `session.value` directly as a prop) therefore stays frozen at whatever files existed when the page loaded, even after a successful Refresh. Separately, `RefreshSummaryPanel.vue` (`src/web/components/RefreshSummaryPanel.vue:46,54,62`) emits `select-file` with the raw `path` string for every Added/Removed/Modified row, which flows into `App.vue`'s `@select-file="selectFile"` binding (`App.vue:1621`) — but `selectFile(fileId: string)` (`App.vue:1066-1090`) resolves via `activeFile(fileId)` which does `session.value?.files.find((file) => file.fileId === fileId)` (`App.vue:590-592`); since `fileId`s match `/^file_[A-Za-z0-9_-]{43}$/` (`src/contracts/api.ts:26`) and paths never do, the lookup always returns `undefined` and the function silently no-ops.

The fix is two isolated, well-scoped edits: (1) add a `sessionClient.getSession()` re-fetch + `session.value = ...` reassignment inside `performRefresh()`, plus selection-preservation logic that matches the previously-selected file by **path** (not fileId, since fileIds can change across a re-fetched snapshot) against the new `session.value.files`, falling back to "next file in tree order" using the existing `createFileTreeModel(...).flatFileRows` ordering; (2) add a path→fileId resolution helper (session-researcher's discretion: a pure function in `src/web/model/`) and thread resolved fileIds into `RefreshSummaryPanel.vue` so its button clicks drive `selectFile(fileId)` correctly, with unresolvable paths rendering as a muted, non-interactive "Removed" row using the already-shipped `ReviewStateBadge kind="disabled"` chip (precedent: `src/web/components/DraftRecovery.vue:130`).

**Primary recommendation:** Re-fetch and reassign `session.value` via `sessionClient.getSession()` immediately after `refreshWorktreeSnapshot()` succeeds inside `performRefresh()` (`App.vue:1401-1424`), before draft reconciliation; add a path→fileId resolver consumed both by the post-refresh selection-preservation logic and by `RefreshSummaryPanel.vue`'s row rendering/emit.

### Pattern 1: Session re-fetch after Refresh (IDENT-04)

**What:** Add a second `sessionClient.getSession()` call inside `performRefresh()`, reassigning `session.value`, mirroring the existing mount-time pattern.
**When to use:** Immediately after `refreshWorktreeSnapshot()` resolves successfully, before the existing `getDraft()`/comment-reconciliation step (so selection-preservation and summary-panel resolution both see the final `session.value.files` before any UI re-renders off stale data).
**Example — current mount-time pattern to mirror (`App.vue:1452-1456`):**
```typescript
sessionClient = createSessionClient();
sessionToken.value = sessionClient.sessionToken;
const loaded = await sessionClient.getSession();
session.value = loaded;
```
**Example — current `performRefresh()` body to extend (`App.vue:1401-1424`), unmodified lines shown for anchoring:**
```typescript
async function performRefresh(): Promise<void> {
  if (sessionClient === undefined || refreshBusy.value) {
    return;
  }
  if (unsavedInlineComposerFile.value !== undefined) {
    dispatchWorkspace({ type: 'add-comment' });
  }
  refreshBusy.value = true;
  try {
    const delta = await sessionClient.refreshWorktreeSnapshot();
    if (delta.added.length + delta.removed.length + delta.modified.length > 0) {
      refreshSummary.value = delta;
    }
    recentlyChangedPaths.value = new Set([...delta.added, ...delta.removed, ...delta.modified]);
    // [NEW] session re-fetch + selection preservation goes here, before getDraft()
    const loadedDraft = await sessionClient.getDraft();
    if (loadedDraft.kind === 'current' && workspace !== undefined) {
      const transition = workspace.replaceComments(reconciledWorkspaceComments(loadedDraft.draft));
      workspaceState.value = transition.state;
      runCommands(transition.commands);
    }
  } finally {
    refreshBusy.value = false;
  }
}
```
**Why safe:** `session.value` is a `shallowRef<SessionResponse>()` (`App.vue:87`); every consumer (`reviewableFiles:211`, `flatFileRows:329`, `activeFile():590-592`, `isUncommittedSession:175`, `isAttachedSession:448`, `filePath():938-940`, template bindings `session.files` at `1772`) reads it reactively via `.value`, so a single reassignment propagates everywhere with no additional wiring.

### Pattern 2: Path-based selection preservation across a fileId-changing re-fetch

**What:** After re-fetching, match the currently-selected file by **path** (not fileId — CONTEXT is explicit that fileIds may change across snapshots) against the new `session.value.files`.
**When to use:** Immediately after the new `session.value` reassignment, before announcing anything.
**Effective-path computation already exists** in `src/domain/file-tree.ts:49-73` (`effectivePath(file)`): deleted files use `oldPath`, added/renamed/copied use `newPath`, everything else prefers `newPath ?? oldPath`. This is the exact same rule `buildFileTree` uses for tree ordering (`src/domain/file-tree.ts:88-103`, `orderProjectedFiles`), so matching against the same `effectivePath.display` string guarantees consistency with what the tree visually shows.
**Tree order for the "next file" fallback** comes from `createFileTreeModel(session.value?.files ?? []).flatFileRows` (`App.vue:329`), whose row order is set by `buildFileTree`'s sort comparator (`src/domain/file-tree.ts:88-103`): primarily by `effectivePath` byte order, then `oldPath`, then `fileId` as a final tiebreaker — i.e., **path**, not fileId, is the primary sort key, so tree order is stable across a re-fetch that only changes fileIds.
**Current `selectFile`/`activeFile` to reuse for re-deriving the file after matching by path (`App.vue:590-592`, `1066-1090`):**
```typescript
function activeFile(fileId: string): SessionFile | undefined {
  return session.value?.files.find((file) => file.fileId === fileId);
}
```
**Announcement wording is locked verbatim by CONTEXT/UI-SPEC** (`25.1-UI-SPEC.md:69-75`): `announce(\`${previousPath} is no longer in the review; showing ${nextPath}\`)`, fired through the existing single live-region (`App.vue:499-502` `announce()`, template region `App.vue:1809-1811`) — fire only when the resolved selection actually differs from the previous one, matching every other `announce()` call site's "only on actual change" discipline (e.g. `watch(hasUnverifiedAnchors, ...)` at `App.vue:477-480`, `watch(patchDrifted, ...)` at `App.vue:485-487`).

### Pattern 3: RefreshSummaryPanel path→fileId resolution (SHELL-05)

**What:** `RefreshSummaryPanel.vue` currently takes `added`/`removed`/`modified` as `readonly string[]` props (paths) and unconditionally renders every row as a `<button class="ui-button" @click="emit('select-file', path)">` (`RefreshSummaryPanel.vue:46,54,62`), with `emit: { dismiss: []; 'select-file': [path: string] }` (`RefreshSummaryPanel.vue:14`). The emitted path flows straight into `App.vue`'s `@select-file="selectFile"` (`App.vue:1621`), and `selectFile(fileId: string)` (`App.vue:1066`) does `activeFile(fileId)` → `session.value?.files.find((file) => file.fileId === fileId)` (`App.vue:590-591`), which never matches a path string against the `/^file_[A-Za-z0-9_-]{43}$/` fileId format (`src/contracts/api.ts:26`) — confirmed no-op.
**Fix (UI-SPEC-locked markup, `25.1-UI-SPEC.md:88-98`):** resolve each path to a fileId in the re-fetched `session.value.files` before rendering; resolved rows stay clickable buttons emitting the **resolved fileId** (not the path); unresolved rows (path absent entirely from the new session) render as a muted, non-interactive `<span>` + `ReviewStateBadge kind="disabled" size="compact" label="Removed"`. A path still present but now deleted (status `kind: 'deleted'`) still resolves to a fileId and stays clickable, opening the deleted-diff state — that is the same `selectFile` → `activeFile` → `file.availability.kind !== 'text'` branch already handled at `App.vue:1077-1083`.
**Emit contract change:** `'select-file': [fileId: string]` instead of `[path: string]` — matches `selectFile(fileId: string)`'s existing signature with zero change needed on the `App.vue` consuming side (`@select-file="selectFile"` at `App.vue:1621` stays as-is; only the payload type/value changes).
**Resolution source of truth:** same `effectivePath(file)` rule used by the tree (`src/domain/file-tree.ts:49-73`) — a path resolves to the `fileId` of whichever `session.value.files` entry's effective path (`newPath` for added/renamed/copied, `oldPath` for deleted, `newPath ?? oldPath` otherwise) matches the summary row's path string.

### Anti-Patterns to Avoid

- **Matching by fileId for selection preservation:** CONTEXT explicitly states fileIds may change across snapshots — any `fileId === fileId` comparison across the re-fetch boundary is wrong by design; must match by `effectivePath.display` (a string).
- **Re-fetching the session before `refreshWorktreeSnapshot()` resolves:** the snapshot must be recaptured server-side first (`POST /api/refresh`) — fetching `/api/session` before that would return the pre-refresh file list again.
- **Second live region or toast for the selection-change announcement:** UI-SPEC is explicit (`25.1-UI-SPEC.md:73`) — reuse the one `<p class="visually-hidden" aria-live="polite">` region (`App.vue:1809-1811`) via the existing `announce()` function; a second region would compete for screen-reader focus.
- **Hand-rolling the "next file in tree order" walk from raw `session.value.files` array order:** `session.value.files` is *not* guaranteed to be in tree-display order (it's whatever order the API returns); `createFileTreeModel(...).flatFileRows` (`App.vue:329`) is the actual displayed order and must be the source for the fallback-selection walk.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Determining a file's "current path" from a `SessionFile` (handling deleted/added/renamed cases) | A new inline `file.newPath ?? file.oldPath` ad hoc check in the new resolver | Reuse the exact rule already encoded by `effectivePath()` in `src/domain/file-tree.ts:49-73` (deleted→oldPath, added/renamed/copied→newPath, else newPath??oldPath) | The tree, the sort order, and any new resolver must agree on what "the path" of a file is, or the new "next file in tree order" fallback and the tree's own display will disagree about which file is selected |
| Walking file order for "next file" fallback | Sorting `session.value.files` manually by path string | `createFileTreeModel(session.value.files).flatFileRows` (already used at `App.vue:329` for `threadOrder`) | Already encodes the exact sort comparator (`buildFileTree`, `src/domain/file-tree.ts:88-103`) that produces the visually displayed tree order, including directory grouping |
| "Inert/non-actionable" row chip | A new custom `<span>` + ad hoc CSS color | `ReviewStateBadge kind="disabled" size="compact"` (already shipped, `src/web/components/ui/ReviewStateBadge.vue:1-54`; precedent `DraftRecovery.vue:130` `label="Read only"`) | Exact existing semantics/color (`--status-disabled-foreground`/`--status-disabled-background`) for "present but non-actionable"; `kind="unavailable"` (the warning-toned chip, precedent `App.vue:1634`/`CommentsTab.vue:116` "Anchor missing") is reserved for a different, alarming semantic and must not be reused here per UI-SPEC |

**Key insight:** every piece this phase needs (effective-path resolution, tree ordering, a disabled-state badge, the single live region) already exists in the codebase from Phases 20–24; the task is wiring, not invention.

## Common Pitfalls

### Pitfall 1: Re-fetching session but not re-deriving `selectedFile`/`selectedContent`

**What goes wrong:** Reassigning `session.value` alone does not change `selectedFile` (a separate `shallowRef<SessionFile>()`, `App.vue:90`) or `selectedContent` (`App.vue:91`) — these hold a *copy* of the old `SessionFile` object, not a live reference, so the identity pill/footer/tree update from the new `session.value`, but the open editor pane and `selectedPath` computed (`App.vue:217`, reads `selectedFile.value?.newPath?.display`) keep showing the stale file object unless `selectFile(...)` (or equivalent) is explicitly re-invoked for the preserved/fallback selection.
**Why it happens:** `selectedFile`/`selectedContent`/`workspace`'s internal `activeFileId` are all derived state that was set once at the original `selectFile()` call and never automatically re-synced from `session.value`.
**How to avoid:** After reassigning `session.value`, explicitly drive the selection-preservation logic through the existing `selectFile(fileId)` (or an equivalent direct `activeFile`+`dispatchWorkspace({type:'switch-file',...})` sequence) for the path-matched (or next-in-tree-order) file, so `selectedFile`, `selectedContent`, and `workspace`'s `activeFileId` all update together.
**Warning signs:** Tree row updates and file count change, but the open diff pane keeps showing deleted/stale content; `selectedPath`/`documentTitle` lag the tree.

### Pitfall 2: Announcing on every refresh instead of only on an actual selection change

**What goes wrong:** If the selection-preservation logic always calls `announce(...)`, it fires even when the previously-selected path is still present (no selection change occurred) — contradicts CONTEXT's explicit wording and the project's "only announce on actual change" convention, and spams the live region on every Refresh.
**Why it happens:** Easy to conflate "ran the re-fetch logic" with "selection actually changed."
**How to avoid:** Only call `announce()` when the resolved post-refresh fileId differs from the pre-refresh fileId (i.e., the path-match failed and the fallback-to-next-file branch executed). Model this the same way `watch(hasUnverifiedAnchors, ...)` (`App.vue:472-483`) and `watch(patchDrifted, ...)` (`App.vue:485-488`) gate their `announce()` calls on an edge/transition, not on every invocation.
**Warning signs:** Live region fires "no longer in the review" text even when the file obviously still exists in the tree.

### Pitfall 3: Resolving `RefreshSummaryPanel` paths against the *pre-refresh* session instead of the newly re-fetched one

**What goes wrong:** CONTEXT and UI-SPEC are explicit the resolution must be against "the re-fetched session" (`25.1-CONTEXT.md:21`, `25.1-UI-SPEC.md:83-84`). If the path→fileId helper runs (or the resolved props are computed) before the new `session.value` assignment lands, every row resolves against stale data, reproducing the same bug class this phase is fixing.
**Why it happens:** `refreshSummary.value` is set earlier in `performRefresh()` (`App.vue:1411-1412`) than this phase's new `getSession()` call needs to land (right after it, per Pattern 1) — if the resolution helper is a `computed` that only reads `session.value` and `refreshSummary.value`, Vue's reactivity means it will automatically re-derive once the new `session.value` lands, so this is only a real risk if resolution is done imperatively/eagerly at the moment `refreshSummary.value` is set rather than reactively.
**How to avoid:** Prefer a `computed()` (consistent with every other derived-from-`session.value` property in `App.vue`, e.g. `reviewableFiles:211`, `flatFileRows:329`) over an imperative one-shot resolution, so ordering within `performRefresh()` cannot desync it from `session.value`.
**Warning signs:** A freshly-added file in the "Added" list renders as "Removed" (or vice versa) immediately after Refresh.

```typescript
// Source: src/domain/file-tree.ts:49-73
function effectivePath(file: SessionFile): ExactPath {
  if (file.status.kind === 'deleted') {
    if (file.oldPath === undefined) {
      throw new Error(`Deleted file ${file.fileId} has no old path`);
    }
    return file.oldPath;
  }
  if (
    file.status.kind === 'added' ||
    file.status.kind === 'renamed' ||
    file.status.kind === 'copied'
  ) {
    if (file.newPath === undefined) {
      throw new Error(`${file.status.kind} file ${file.fileId} has no new path`);
    }
    return file.newPath;
  }
  const path = file.newPath ?? file.oldPath;
  if (path === undefined) {
    throw new Error(`File ${file.fileId} has no effective path`);
  }
  return path;
}
```

   - What we know: `selectFile(fileId)` short-circuits to `loadFile(file)` only if `workspace?.getState().activeFileId === file.fileId` (`App.vue:1085-1088`); if the fileId changed (even though the path is the same), this check fails and a full `dispatchWorkspace({type:'switch-file',...})` occurs instead (`App.vue:1089`).
   - What's unclear: Whether re-running `selectFile` unconditionally after every Refresh (even when the path-matched fileId is identical to the pre-refresh fileId) causes any observable flicker/re-fetch of file content that CONTEXT's "preserve ... in-progress edit text" requirement would consider a regression.
   - Recommendation: Guard the re-selection call so it's skipped entirely when the matched fileId is unchanged from `selectedFile.value?.fileId` — only invoke the selection-sync path when the fileId differs or no match was found, minimizing unnecessary content re-fetches and avoiding any interference with in-progress edit text.
