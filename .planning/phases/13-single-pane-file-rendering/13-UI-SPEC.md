## Color

### 60/30/10 — unchanged allocation, reused

| Role | Token | Usage in this phase |
|------|-------|-------|
| Dominant (60%) | `--surface-canvas` | Single-pane Monaco editor background — identical token the diff editor already uses, applied automatically because `applyCumpaTheme()` registers one global Monaco theme (`src/web/monaco/theme.ts:108-110`); the plain editor needs no separate theme wiring |
| Secondary (30%) | `--surface-panel` | Single-pane side-label strip background (reused `.diff-workspace__side-labels` rule) |
| Accent (10%) | `--interactive-accent` / `--focus-ring` | Keyboard focus and active comment anchor rail inside the single-pane editor — identical consumer mapping as the diff editor; no new accent use |
| Destructive | `--destructive-foreground` | No new destructive action this phase (D-14); token unused here |

Accent reserved for: focus ring, Monaco cursor, active comment anchor rail, text selection — identical list to `10-UI-SPEC.md:108`. This phase adds no new accent consumer.

### Status badge tones — unchanged, reused by letter only

| Status | Existing tone class | Token |
|--------|----------------------|-------|
| `added` | `.status-badge--added` | `--status-added-foreground/background/border` |
| `deleted` | `.status-badge--deleted` | `--status-deleted-foreground/background/border` |
| `type-changed` | `.status-badge--modified` (existing "Mode" mapping in `StatusBadge.vue:22-24`) | `--status-modified-foreground/background/border` |

**No new tone is introduced.** D-02 explicitly forbids a whole-pane added/deleted tint — the single-pane Monaco editor renders with the plain `editor.background` (`--surface-canvas`) only, the same canvas color used for unchanged lines today. Color continues to live only in the already-existing badge chip, never in the editor canvas or page chrome.

### Critical constraint: D-02 compliance is structural, not a style override

Because `monaco.editor.create()` (plain editor, no diff model) applies no `insertedLineBackground` / `removedLineBackground` decorations — those are diff-editor-only Monaco options — a plain editor is tint-free by construction once it shares the registered Cumpa theme. Do **not** add any custom decoration, CSS class, or `addLineDecorations` call that reintroduces a whole-line add/remove fill. If a future diagnostic needs a line marker in single-pane files, it must use a non-color channel (text, icon) per the Phase 08/10/09 "never color alone" rule — none is required by this phase.

### Type-changed `<kind>` derivation (resolves D-06's open research question)

The comparison contract (`src/contracts/comparison.ts`) exposes `oldMode`/`newMode` as `GitModeSchema` (6-digit octal string) on every `ChangedFile`. The codebase already derives a type/kind from this mode in three places (`src/git/availability.ts:15-18,55-59`, `src/domain/exact-patch.ts:432-433`, `src/git/inventory.ts:45-50`), establishing a precedent mapping. Phase 13 reuses that exact mapping for the header note, applied to `oldMode`:

| `oldMode` | `<kind>` text |
|-----------|---------------|
| `120000` | `symlink` |
| `160000` | `submodule` |
| `100644` | `file` |
| `100755` | `executable file` |
| any other value | the raw mode string, e.g. `was mode 040000` (generic fallback per D-06's instruction — no new git plumbing) |

This keeps the header a single source of truth derivable from data already on the wire (`oldMode`) with no new API call, consistent with D-06's "fall back to `was <old mode>`... rather than adding git plumbing."

## Component Contracts

### `StatusBadge.vue` (D-09)

- No change to the visible letter, tone, or markup structure.
- Extend the `.visually-hidden` label only for the three single-pane statuses, appending `, single pane` to the existing label string (`Added` → `Added, single pane`; `Deleted` → `Deleted, single pane`; `Mode changed` → `Mode changed, single pane`).
- `modified`, `renamed`, `copied` labels are unchanged (D-11: no extra label on side-by-side files).
- This requires the badge to know layout mode (single-pane vs. side-by-side), which is a derived boolean from `status.kind ∈ {added, deleted, type-changed} AND reviewable`, not a new prop shape beyond what the parent already computes for layout routing.

### `ActiveFileToolbar.vue` (D-10)

- Replace the current raw `{{ selectedFile.status.kind }}` text (`ActiveFileToolbar.vue:54`) with:
  - **Single-pane files:** `<StatusBadge>` + the layout label text from the Copywriting Contract above, in that order (badge first, label second), separated by `--space-1` (`4px`).
  - **Side-by-side files (`modified`, `renamed`, `copied`):** keep today's existing presentation unchanged (D-11) — do not introduce a layout label for them in this phase.
- Typography: label text uses the Body role (`14px/21px`, `400`, `var(--font-ui)`), matching the existing `.review-toolbar__status` class (no new class needed beyond conditional content).
- Accessible name: the header `<h1>` filename plus adjacent badge/label text must remain readable in document order by a screen reader; no `aria-hidden` on the new label (unlike the Monaco side-label strip, which stays `aria-hidden` per D-12 note below).

### Single-pane side-label strip (D-12)

- Reuse `.diff-workspace__side-labels` exactly, but render **one** `<span>` child instead of two, spanning full width (the existing grid is `1fr 1fr`; a single-pane instance uses `grid-template-columns: 1fr` for that one row — a CSS modifier class, not a new token).
- Content: `{Side} · {short oid}` where `{Side}` is `Head` (added, type-changed) or `Base` (deleted), matching the existing side-by-side label format (`visibleSides.original`/`visibleSides.modified` pattern in `DiffWorkspace.vue`).
- No `− REMOVED` / `+ ADDED` cue span — those signed cues exist to distinguish two columns; a single full-width pane has no counterpart column to contrast against, so D-02's "no added/removed tint" extends to this strip: it states identity (`Head`/`Base`) only, no change-sign text.
- Stays `aria-hidden="true"` exactly as today (`DiffWorkspace.vue:324`), because — per `13-CONTEXT.md:38` — the accessible side identity for single-pane files comes from the header text (D-10, now carrying `· Head only` / `· Base only`) and the comment composer (`CommentComposer.vue:28`, unchanged), not from this strip. Outer `<section>` `aria-label` must be updated for single-pane files to a single-side pattern, e.g. `` `${path}: head only` `` / `` `${path}: base only` ``, mirroring the existing two-side patterns at `10-UI-SPEC.md:192-193`.

### `ReviewToolbar.vue` (D-04)

- The **"Change navigation"** group (`previousChange`/`nextChange`, `ReviewToolbar.vue:47-71`) has no meaning for a file with no hunks. Hide this entire `<div class="review-toolbar__group" aria-label="Change navigation">` when the active file is single-pane.
- The **"File navigation"** group (`previousFile`/`nextFile`, lines 22-46) stays visible — it is file-level, not diff-only, and continues to work identically.
- No wrap-lines control exists yet in this codebase (`DEFER-03`, deferred at v1.6 close) — there is nothing to keep or hide for "wrap" today; when it ships later it is file-level per `13-CONTEXT.md:24` and must not be hidden for single-pane files.
- Monaco's native hidden-region controls (`Show Unchanged Region`, edge reveal affordances, `Show All Unchanged Regions`) are diff-editor-only APIs; they simply do not exist on a plain `ICodeEditor` instance, so no explicit hiding code is needed for them beyond using the plain editor per D-01 — confirm no custom wrapper re-adds equivalent controls for single-pane files.

### Empty-file notice (D-07)

- Use the existing `InlineNotice.vue` component, not a new notice primitive.
- Props: `tone="neutral"` (informational, not a problem state — matches the component's tone semantics: neutral/information for non-error disclosure), `role="note"` (default).
- Content: single `<p>Empty file (0 bytes)</p>` inside the default slot, matching the existing `<InlineNotice>...<p>...</p></InlineNotice>` usage pattern seen throughout the codebase (e.g. `DriftExportAcknowledgement.vue`, export panel states).
- Placement: inside the single-pane host, in place of the Monaco editor instance (no editor is mounted for a 0-byte file — "no blank editor" per D-07). The side-label strip (D-12) still renders above it, since side identity still applies to a 0-byte added/deleted file.
- No comment target lines exist for a 0-byte file per D-07 — the composer/anchor affordance must not appear over this notice.

### Single-pane Monaco pane (D-01, D-03)

- New creation path parallel to `createDiffEditor` in `src/web/monaco/diff-adapter.ts` (or a sibling module — left to planning per CONTEXT.md discretion), using `monaco.editor.create(container, options)`.
- Line numbers: single column, showing only the anchor side's numbers (Head for added/type-changed, Base for deleted) — i.e. `lineNumbers: 'on'` against the one model that is mounted, not the diff editor's dual original/modified line-number lanes.
- Theme: no separate theme call needed — `applyCumpaTheme()` already registers one global Monaco theme consumed by any editor instance created afterward (`theme.ts:108-110`); same `editor.background` (`--surface-canvas`), same `editorLineNumber.foreground` (`--text-line-number`), same syntax token colors as the diff editor's original/modified sub-editors.
- Code density: reuse the exact same `CODE_DENSITIES` table and responsive breakpoints (`wide`/`default`/`compact`) already defined in `diff-adapter.ts` — no new density values for single-pane content.
- Comment gutter / view zones / decorations: must attach to this plain `ICodeEditor` using the same anchor/decoration APIs already used for the diff editor's `originalEditor`/`modifiedEditor` sub-editors (both are already plain `IStandaloneCodeEditor` instances internally per `diff-adapter.ts:94-96`), so no new decoration contract — the single-pane editor is architecturally the same editor type the diff adapter already wires comments onto, just not paired with a diff model.
- Focus ring: identical `2px` `--focus-ring` inset treatment as the diff editor (`10-UI-SPEC.md:243`), no new focus style.
- Current comment anchor: identical `3px` `--selected-rail-width` accent rail as the diff editor (`10-UI-SPEC.md:252`).

## Accessibility Contract

- Single-pane and side-by-side files must be distinguishable without color in two places simultaneously: the tree row's visually-hidden `StatusBadge` label (D-09) and the file header's layout label text (D-10) — neither is conveyed by color alone, consistent with the Phase 08/09/10 "never color alone" invariant.
- The single-pane `<section>` accessible name states the single side explicitly (see Component Contracts → side-label strip) — never a generic "diff" label for a pane with only one side.
- Screen-reader users get side identity from: (1) the header layout label (always visible, not `aria-hidden`), (2) the composer's existing `· Base line N` / `· Head line N` text per comment. The `aria-hidden` side-label strip is a sighted-user convenience only, matching the existing side-by-side pattern exactly.
- `ReviewToolbar`'s hidden "Change navigation" group must be removed from the accessibility tree (not just visually hidden) when hidden for single-pane files — use `v-if`, not `visibility:hidden`/`display:none` toggling via CSS class, consistent with the existing Vue conditional-render pattern used elsewhere in this toolbar.
- Empty-file `InlineNotice` renders as a `role="note"` region, discoverable in document order, not an `alert` (it is not an error).
- Focus order is preserved: file → side identity → content (or empty notice) → comment composer, matching the existing file → Base → Head reading order invariant from Phase 08 (`08-UI-SPEC.md:265`).
- `prefers-reduced-motion` / `forced-colors` behavior is inherited unchanged from Phase 08/10 — this phase introduces no new motion and no new color-only state.

No new breakpoint. Single-pane files use the identical `640px` minimum canvas width, identical compact (`≤1050px`) and mobile (`≤760px`) code density switches already defined for the diff editor (`10-UI-SPEC.md:220,229-235`), since the single-pane editor is created with the same `CODE_DENSITIES` table. The single-pane side-label strip collapses to one full-width span at every breakpoint (there is no second column to stack or hide).
