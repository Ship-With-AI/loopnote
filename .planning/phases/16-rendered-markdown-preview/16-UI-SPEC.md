### Renderer extension authority

`src/web/model/markdown-preview.ts` (14 lines today) is the single normative renderer for MDV-04. It stays `html:false`, keeps its existing `validateLink`/`link_open` override unchanged (D-10 reuses it verbatim), and gains exactly four additions, all implemented as **local markdown-it core rules in this same file — no new npm dependency**:

1. A block rule that detects a leading `---\n…\n---` front-matter span and emits it as a single `fence` token (`info: 'yaml'`) before any other block rule runs, so it renders through the existing fenced-code-block path (D-11) instead of being misparsed as an `<hr>` + heading.
2. A core rule (post-inline) that rewrites `list_item_open` → paragraph text matching `/^\[([ xX])]\s+/` into a disabled, read-only checkbox + stripped text (GFM task lists, D-11).
3. A `renderer.rules.image` override implementing D-09 (remote → placeholder text; relative → content-route `src` rewrite; see Component Contracts).
4. Exposure of each rendered block's markdown-it `map` range as a `data-source-start`/`data-source-end` attribute pair on its outermost rendered element (D-05/D-02 anchor + marker plumbing).

**Rationale for "no third-party plugin" (resolves the open plugin-choice question):** confirmed by direct execution against the pinned `markdown-it@14.3.0` — GFM tables already render correctly with **zero plugin** (markdown-it's default preset includes the `table` core rule); only task-list checkboxes and front-matter need new behavior, and both are small, self-contained rules (≈20–40 lines each) on a security-hardened renderer module. Adding a third-party block/inline-rule plugin here would add unaudited surface to the one module this phase's XSS/link-safety requirement (MDV-04) depends on — against the hardened-renderer precedent already set by `validateLink`. Local rules keep the audit surface identical to today's.

## Typography

Zero new sizes, zero new weights. Reuses exactly the four Phase 08 roles (`--font-size-metadata`/`--font-size-code`/`--font-size-body`/`--font-size-page-heading`) and the two Phase 08 weights (`--font-weight-regular`/`--font-weight-semibold`):

| Role | Size | Weight | Line height | Font | Usage in phase |
|------|------|--------|-------------|------|-----------------|
| Page heading | `21px` | `600` | `31.5px` | `var(--font-ui)` | Rendered `h1` only |
| Body (bold) | `14px` | `600` | `21px` | `var(--font-ui)` | Rendered `h2`–`h6` (all five levels render at this single size; see rationale below); table header cells; marker tag text |
| Body | `14px` | `400` | `21px` | `var(--font-ui)` | Rendered paragraphs, list items, table cells, blockquote text |
| Code | `13px` | `400` | `26px` | `var(--font-mono)` | Fenced code blocks, YAML front-matter block, inline `code` spans |

**Heading-level rationale (resolves a typography question not answered upstream):** the app's type scale is capped at four sizes across the whole product (Phase 08's explicit ceiling). Giving `h1`–`h6` six distinct sizes would add a fifth and sixth size. Instead `h1` maps to the existing Page-heading role (the only role already larger than Body), and `h2`–`h6` all render at Body/600 — differentiated from each other only by vertical rhythm, not size: `h2` gets `margin-top: var(--space-6)`, `h3` gets `var(--space-4)`, `h4`–`h6` get `var(--space-2)`. `h1` additionally gets a `1px solid var(--border-default)` bottom rule (reused token, no new color) and `margin-top: var(--space-6)`. This keeps the semantic heading hierarchy intact for screen readers/outline navigation while staying inside the declared ceiling — same discipline Phase 13 applied ("no fifth size or third weight introduced anywhere in this phase").

- Remote-image placeholder text and comment-trigger tooltip text use the Metadata role (`12px`/`400`/`18px`, `var(--font-mono)` for the URL portion only), matching the existing `.diff-workspace__gutter-action::after` tooltip (`styles.css:1617-1634`) and `.availability-marker` convention.
- Paths, line numbers, and OIDs in any new copy stay on the code/mono stack per the existing invariant (`08-UI-SPEC.md:104`).

**Marker token mapping (resolves D-02's "which Phase 08 tokens" question):** the three-way `Added`/`Removed`/`Changed` vocabulary maps 1:1 onto the Phase 08 `--status-added-*` / `--status-deleted-*` / `--status-modified-*` triplets already used by `StatusBadge.vue` for the identical three words (`Added`/`Deleted`→`Removed` text/`Modified`→`Changed` text) at the file-tree level. This was chosen over the Monaco-specific `--diff-addition-foreground`/`--diff-deletion-foreground` pair (used by `.monaco-diff-change-bar--*`) because that pair is binary (only two tones) and cannot represent `Changed` as a third state without inventing a new color; the status triplet already has exactly three members and is the more semantically exact reuse.

### Marker word → tag copy (exact)

| Classification | Marker word | Token triplet |
|---|---|---|
| Block whose range overlaps a pure deletion (content exists on this side's source but not the other) | `Removed` | `--status-deleted-*` |
| Block whose range overlaps a pure addition (content exists on this side's source but not the other) | `Added` | `--status-added-*` |
| Block whose range overlaps a modification (content exists on both sides within the same change, text differs) | `Changed` | `--status-modified-*` |
| Block outside every change range | *(no marker)* | — (renders plain, per D-01) |

## Component Contracts

### `RenderedMarkdownView.vue` (new component — D-01, D-02, D-04, D-05, D-06, D-07, D-11)

- Props: `content: string` (raw markdown source for this side), `changes: readonly ILineChange[]` (the same Monaco line-change data D-01 maps marker ranges from), `side: DiffSide`, `comments`, `composer`, `mutationsLocked` — same comment/composer prop shape `DiffWorkspace.vue` already passes into its Monaco host, so `CommentComposer.vue` is reused with **zero changes**.
- Renders `renderMarkdownPreview(content)`'s HTML into block-wrapped DOM: each top-level block (paragraph, heading, list item, table row, fenced code block, blockquote paragraph — the granularity D-05 names) is wrapped in `<div class="rendered-block" tabindex="0" :data-start="…" :data-end="…">`, keyboard-focusable per D-04 ("Blocks are keyboard-focusable (Tab/arrow navigation)").
- **Block markers (D-01/D-02):** a block whose `[data-start, data-end]` range overlaps a classified change range (see Color → marker table above) gets `class="rendered-block--added|removed|changed"`, which applies:
  ```
  border-left: 2px solid var(--status-{added|deleted|modified}-foreground);
  ```
  plus a small leading tag chip reusing the existing `.status-badge`/`.availability-marker` chip pattern (`styles.css:382-397`: `display:inline-flex; min-height:32px; padding: var(--space-1) var(--space-2); border:1px solid var(--token-border); font: Metadata/600;`) with `background: var(--status-{…}-background); color: var(--status-{…}-foreground); border-color: var(--status-{…}-border);` and text content `Added`/`Removed`/`Changed`. The chip sits above the block content (own line), not inline with it, so it never truncates or wraps into prose. **Never color-only**: the word is always present, matching the Phase 08/13 invariant.
  - A block overlapping no change range renders with no border, no chip — plain, per D-01.
  - Nested blocks inside a quote (e.g. a `blockquote`'s own `2px` left rule, see Typography/Table/Code below) and the marker's `2px` rule are two separate elements at the block boundary; they are expected to appear concentrically when both apply (native nesting, not a conflict).
- **Comment trigger (D-04):** a `button.diff-workspace__gutter-action` (verbatim reused class — zero new CSS) appears on hover/focus of a `.rendered-block`, positioned via CSS (`position: absolute; inset-inline-end: var(--space-2); inset-block-start: var(--space-1);` relative to the block, not the Monaco pixel-offset `top` style `DiffWorkspace.vue:379` uses, since there is no line-pixel geometry in a rendered pane) — same `32×32`, same border/background/icon-color/tooltip-via-`::after` behavior, same `:disabled` wiring to `mutationsLocked`. Clicking opens `CommentComposer.vue` anchored to that block's `[data-start, data-end]` range (D-05/D-06: exactly one block, no multi-block selection — `CommentComposer.vue` receives the same single-range anchor shape it already accepts from Monaco line selections).
- **Existing comments (D-07):** rendered as `conversation-card` elements, structurally **identical, unchanged** to `DiffWorkspace.vue:145-157`'s `h('section', {class:'conversation-card inline-accepted-comment', …})` render function — same header/body/footer markup, same `Saved locally` footer badge. Insertion point: immediately after the `.rendered-block` whose range is the first block overlapping the comment's anchor range (D-07: "shows on the first overlapping block"), always expanded (no collapse control — D-07 is explicit).
- **Side (D-08):** identical rule to code view — side-by-side left pane anchors `base`, right pane anchors `head`; single-pane follows the Phase 13 `singlePaneSideFor` rule. No new side logic; `RenderedMarkdownView` receives `side` as a prop exactly like the Monaco adapter does today.
- **Tables (D-11):** `<table>`/`<th>`/`<td>` get one new minimal rule set (no existing table styling found anywhere in `styles.css` to reuse) — `border-collapse: collapse; border: 1px solid var(--border-default);` on `table`, `th`, `td`; `padding: var(--space-2) var(--space-4);` on cells; `th` uses the Body/600 role and `background: var(--surface-panel)`.
- **Task lists (D-11):** rendered checkbox is `<input type="checkbox" disabled :checked="…">` immediately before the stripped list-item text, inline, no new size — `disabled` conveys read-only to assistive tech via the standard disabled-control semantics, no extra `aria-readonly` needed.
- **Front matter (D-11):** renders through the existing fenced-code-block path (see Renderer extension authority above) — i.e. **identical styling to any other fenced code block**, no special-casing in this component.
- **Code blocks / inline code (D-11, new minimal styles within the existing scale):**
  - Fenced block: `<pre><code>` with `background: var(--surface-panel); border: 1px solid var(--border-default); border-radius: var(--radius-control); padding: var(--space-4); overflow-x: auto;` and the Code typography role (`13px`/`400`/`26px`, `var(--font-mono)`).
  - Inline `code`: `background: var(--surface-panel); border-radius: var(--radius-control); padding: 0 var(--space-2);` with the Code typography role, inline (no block padding).
  - Blockquote: `border-inline-start: 2px solid var(--border-default); padding-inline-start: var(--space-4); color: var(--text-muted);` (reuses the same `2px` left-rule width as the Monaco diff change-bar and the D-02 marker, applied here to a semantically different, neutral-toned use).
- **Links (D-10):** reuses `renderMarkdownPreview`'s existing `link_open` rule unchanged — `http(s):`/`mailto:` clickable with `target="_blank" rel="noopener noreferrer"`; every other `href` renders as non-clickable text showing the target (the renderer already strips interactivity for non-validated links by never marking them `<a>` — confirmed by the existing `validateLink` gate at `markdown-preview.ts:9`).
- **Images (D-09):** `renderer.rules.image` override:
  - `src` matching `^https?:` → render the inline placeholder `<span class="rendered-markdown__remote-image">` with the exact copy from the Copywriting Contract above; never issues a `fetch`.
  - Relative `src` → rewritten to the new same-origin image content route (see Server below); rendered as a normal `<img>` with the original `alt` text, loaded from `'self'` under the unchanged CSP (`img-src 'self'`, confirmed in `src/server/security.ts:22` — **no CSP directive changes required**, D-09's "no `img-src` widening" is satisfied automatically by keeping the new route same-origin).
  - A relative `src` that resolves outside the session's file set/repo (per the Phase 15 path-safety rules) renders the same placeholder text as a remote image, since Cumpa cannot safely serve it.

### `ActiveFileToolbar.vue` (D-02 toggle placement)

- Add the Source/Rendered button pair to the existing `.review-toolbar__active-file` flex row (`ActiveFileToolbar.vue:74-96`), positioned after the status badge/label/counts and before the existing `Hide files`/`Show files` button, gap `--space-1` matching the row's existing child spacing.
- Only rendered when the active file's extension is `.md` or `.markdown` (D-12); every other extension shows neither button and the file always displays source — no `v-if` flicker since this is a static per-file computed, same pattern as the existing `layoutLabel`/`counts` computeds in this file.
- Markup: two `<button type="button" class="ui-button" :aria-pressed="mode==='source'|'rendered'">Source|Rendered</button>` — **zero new CSS**: the global `button[aria-pressed="true"]` rule (`styles.css:538-542`) already supplies the pressed-state treatment used everywhere else in the app.
- Toggle state is **per file, in-memory for the session** (not persisted across reloads), per the CONTEXT.md discretion resolution. In side-by-side layout, one toggle switches both panes (single source of truth, not a per-pane control).

### `DiffWorkspace.vue` (host swap, D-01 both-sides rendering)

- Gains a `mode: 'source' | 'rendered'` prop (lifted from `ActiveFileToolbar.vue`'s new toggle via the parent, same prop-threading pattern as `singlePaneSide`).
- When `mode === 'rendered'` and the file is Markdown: mounts `RenderedMarkdownView` instead of the Monaco host, **once per visible side** — both single-pane (`singlePaneSide !== undefined`, one instance) and side-by-side (two instances, left=`base`, right=`head`, per D-01 "both Base and Head render"). The existing `.diff-workspace__side-labels` strip (`Head`/`Base` text, `9px/18px` padding exception inherited from Phase 08/13 — `13-UI-SPEC.md:57`) stays mounted above each pane unchanged.
- When `mode === 'source'`: existing Monaco behavior, completely unchanged (D-02/D-12 confirm no visual change to the source-view contract already shipped in Phases 08–14).
- **Scroll sync (D-03 — resolves the one genuinely open decision):** **block-aligned, best-effort, enabled by default** when both panes show `Rendered` in side-by-side layout. Rationale: Monaco's own diff editor already synchronizes scroll between original/modified in Source mode (native Monaco behavior); keeping an equivalent synced-scroll expectation in Rendered mode preserves the same mental model across the toggle rather than surprising the reviewer with independent scrolling only in one mode. Mechanism (visual contract, not full algorithm — implementation detail left to the planner): on scroll of either pane, identify that pane's topmost visible `.rendered-block`, find the block in the other pane whose `[data-start, data-end]` range is nearest (by range overlap, falling back to nearest `data-start`), and scroll that block to the same relative viewport offset. This degrades gracefully (no forced alignment, no error state) when block counts differ between Base and Head — an unmatched scroll position is acceptable, never a hard error.

### Server — image content route (D-09)

- The existing `GET /api/files/:fileId/content` route (`routes.ts:311-337`) is **not reused as-is**: it requires `metadata.availability.kind === 'text'` and returns parsed/typed content, not raw image bytes with a content-type header — unsuitable for binary image bytes.
- A **new route** is required: `GET /api/files/:fileId/image` (or equivalent path under the same `/api/files/:fileId/*` family for consistency), serving raw bytes with the correct `Content-Type` resolved from the file extension (`image/png`, `image/jpeg`, `image/gif`, `image/svg+xml`, `image/webp` — the minimal common set; anything else renders the D-09 placeholder, never served). Must apply the same path-safety resolution as the existing content/lookup routes (`OpaqueFileIdSchema`, `capabilities.lookup`) plus the Phase 15 path-safety rules (resolve inside the session's file set/repo, reject traversal/symlink escapes) — same `realpath`/per-segment precedent `15-CONTEXT.md:30` names.
- **No CSP change**: the route is same-origin, so `img-src 'self'` (unchanged, confirmed at `security.ts:22`) already permits it.

## Accessibility Contract

- Toggle state conveyed by visible text (`Source`/`Rendered`) **and** `aria-pressed`, never by color alone — direct CONTEXT.md requirement (`16-CONTEXT.md:39`), satisfied by reusing the existing color-agnostic `button[aria-pressed="true"]` rule.
- `.rendered-block` elements are in the Tab order (`tabindex="0"`) so the D-04 gutter button is reachable without a mouse, per `16-CONTEXT.md:26`. Focus order within a pane follows document order (top block → bottom block), matching the existing "file → Base → Head reading order" invariant (`08-UI-SPEC.md:265`) at the pane level.
- Block markers (`Added`/`Removed`/`Changed`) are always spoken as part of the block's accessible name/content via the visible tag chip text — never `aria-hidden`, consistent with the Phase 08/13/14 "never color alone" invariant applied throughout.
- Remote-image placeholder replaces the `<img>` entirely (not an `<img alt>` with a broken `src`) so screen readers announce the placeholder text directly rather than an image load failure — this is more informative than a native broken-image announcement.
- Task-list checkboxes use native `disabled` semantics (assistive tech already announces disabled controls); no extra ARIA needed.
- `CommentComposer.vue` and the `conversation-card` thread markup are reused byte-for-byte, so all existing accessibility behavior (focus management, `role`, live-region wiring) is inherited unchanged — this phase adds no new accessibility surface there.
- Scroll-sync (D-03) never steals focus and never triggers an `aria-live` announcement — it is a visual convenience only, matching the "Never auto-refresh"/no-surprise-announcement precedent set for passive indicators in `14-UI-SPEC.md:225`.
