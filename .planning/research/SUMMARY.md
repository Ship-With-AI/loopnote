# Project Research Summary

**Project:** Loopnote
**Domain:** Browser-based local-first code/artifact review workspace — VS Code-inspired workbench redesign (Vue 3 + Vite + Monaco diff editor), desktop only
**Researched:** 2026-11-04
**Confidence:** HIGH

## Executive Summary

v2.1 is a **restyle-and-recompose** of an already-shipped review workspace, not a rewrite. All four researchers confirm the same shape: state machines, the Monaco diff core, the API client, and the draft/export contract stay untouched; what moves is *where chrome lives* (title bar / resizable side bar / bottom panel / status bar instead of header band / toolbar rows / modal dialogs / footer) and *how comments render* (many expanded-by-default Monaco view-zone threads instead of one active composer zone). STACK.md's headline finding is that this redesign needs **zero new runtime dependencies** — icons, resizable sashes, tree rendering, and popovers are all achievable in existing Vue/Monaco/CSS, matching the sketches' own plain-CSS/JS implementations. The one real toolchain gap is `.vue` typechecking, broken today by a genuine TypeScript 7.0 / `vue-tsc` incompatibility (reproduced live in the repo), which both STACK.md and ARCHITECTURE.md agree must be fixed in the first phase, before the milestone's heaviest `.vue` churn (App.vue decomposition, multi-zone comment threads) lands untyped.

The recommended approach is dependency-conservative and sequencing-disciplined: land the typecheck fix and the new CSS token root first (cheap, foundational, unblocks `verify:semantic-css` and every chrome component), build the shell skeleton around *existing* presentational components before touching their internals, then take on the one genuinely hard, novel piece of engineering — multi-zone Monaco comment threads — as its own late, gated phase with an explicit go/no-go pointer-event spike before committing to "many expanded threads per file" as the interaction model.

The key risks are concentrated in three places: (1) the multi-zone Monaco adapter rework (view-zone height desync between Base/Head panes, DOM-pointer-events-through-zone unreliability, zone churn on draft reconciliation dropping in-progress replies — all flagged as *already known, already documented* limitations in the project's own prior design research, not new discoveries); (2) App.vue's 1,468-line template silently dropping one of five distinct session-kind behaviors during decomposition (committed, exact-patch, uncommitted, standalone, attached/agent-driven each have materially different shell behavior — this exact failure class has recurred in prior milestones); and (3) five explicit sketch gaps the design docs themselves left unresolved (standalone-session identity pill, Finish-placement, Markdown toggle placement, support-entry placement, open-thread default collapse state) that roadmap/requirements must decide before the phases that depend on them can be planned, not improvised mid-implementation.

## Key Findings

### Recommended Stack

No new `dependencies` (runtime bundle) entries are needed for this milestone — icons extend the existing zero-dependency `UiIcon.vue` SVG component rather than adopting `@vscode/codicons` (3.5MB, visual-mismatch risk); resizable sashes are a ~60–80 line pointer-event composable rather than `splitpanes`; popovers are manual `getBoundingClientRect()` positioning (matching the sketches' own fixed single-trigger layout) rather than `@floating-ui/vue`; tree virtualization is explicitly deferred (412 flat 22px rows is within unvirtualized-DOM budgets, and the sketches themselves flag virtualization as untested, not a confirmed requirement). The only dependency changes are `devDependencies`, to fix `.vue` typechecking (see Resolved Conflict 1 below).

**Core technologies (all unchanged, confirmed against installed `package.json`):**
- Vue 3.5.39 + Vite 8.1.4 — workbench UI framework and dev/build pipeline, no breaking changes needed.
- Monaco Editor 0.55.1, `createDiffEditor` — diff rendering and view-zone mechanism; `diff-adapter.ts`'s existing paired-zone technique (`createComposerZone`/`createSpacerZone`/`growPairedZones`) is the proven pattern to extend to multiple keyed zones, not replace.
- Zod — unchanged contract/validation layer; a reply-data-model decision (see Open Question below) is the only place this milestone might touch `ReviewDraftV1Schema`.
- Vitest + Fastify `inject()` + Playwright — unchanged test stack; the milestone's main test-impact driver is selector/accessible-name churn across ~6,000+ lines of e2e/integration specs that assert on components being replaced or restyled.

### Expected Features

**Must have (table stakes, all P1):** 32px title bar with centered Base→Head identity pill + click-to-open details/drift/refresh popover; resizable files-only side bar (⌘B, drag sash, double-click reset, no activity bar); 22px-row Explorer-density changed-files tree (compact folders, M/A/D column, hover-only `+/−` counts and comment badges, path filter behind a funnel toggle, view-options menu, footer totals); icon-only 35px editor title bar (prev/next change, prev/next file, inline/side-by-side, comment nav) bundled with the DEBT-01 `role="group"` accessibility fix on the same toolbar surface; inline Monaco view-zone comment threads with Open/Resolved/Anchor-moved state chips, resolve/reopen/delete/reply (backend contract for all four already exists and shipped before being stripped from the UI by quick task `260915-jbv` — this significantly de-risks the item relative to its LARGE complexity rating, since the hard part is the view-zone/overlay mechanism, not unknown backend behavior); cross-file thread navigation (⌥F9/⇧⌥F9, exact VS Code default keybinding); bottom panel (Comments/Summary/Export tabs) closed-by-default, ⌘J-toggleable, reachable from four entry points; export readiness → stale-anchor acknowledgement gate → receipt, relocated into the panel unchanged; `DESIGN.md` rewritten to describe the shipped shell.

**Differentiators (already built, carried forward, UI-only work):** durable drift-detectable comment anchors with export-blocking "Anchor-moved" acknowledgement (no VS Code/GitHub/GitLab/Gerrit analogue); canonical JSON + generated Markdown dual export receipt; five-session-kind identity pill (branches/staged/unstaged/working-tree/exact-patch) including "cannot refresh" framing for frozen snapshots.

**Defer (beyond v2.1):** full two-mode (highlight vs. filter) Explorer-style tree filtering; tree virtualization (only if real-fixture testing shows jank); hunk jump-position indicator ("3 of 12", tracked separately as DEFER-02); narrow/phone-width layout (explicitly accepted debt below 1050px per PROJECT.md scope decision); per-file "viewed" tracking is flagged **optional/separable** — see Flag 3 below.

**Explicit anti-features:** no activity bar (one sidebar view doesn't justify 48px of permanent chrome); no duplicate "Review" side-bar view; no blocking Finish-review modal overlay; no tall persistent identity header/breadcrumb/status-bar-only identity placement; no always-visible per-row line-count columns; no color-only M/A/D indication (WCAG 1.4.1).

### Architecture Approach

The system is one Vue 3 SPA (`src/web/main.ts` → `App.vue`, 1,468 lines) served by a local Fastify API, with no router and no store library — state lives in `App.vue`'s refs/computeds plus two hand-rolled state machines (`workspace-state.ts`, `review-draft-state.ts`). The redesign decomposes `App.vue` into a slim session-bootstrap/state-owner (~500–700 target lines) plus a new `WorkbenchShell.vue` layout host, with five new chrome-only components (`TitleBar.vue`, `IdentityPill.vue`, `IdentityPopover.vue`, `SideBar.vue`, `BottomPanel.vue`, `StatusBar.vue`, `CommentThread.vue`, `ViewOptionsMenu.vue`) living in a new `components/workbench/` directory, while existing diff/tree/panel components (`FileTree.vue`, `DiffWorkspace.vue`, `SummarySection.vue`, `ExportSection.vue` and its four children) are restyled or extended in place, not rewritten. The hardest structural change is `diff-adapter.ts`'s zone model moving from one singular `originalZone`/`modifiedZone` pair to a `Map<anchorKey, zone>` per editor, so multiple comment threads can render simultaneously, independently height-grown, and stay line-aligned across Base/Head. Three invariants must survive the rebuild unmodified: Monaco stays sole diff authority (adapter extends, never bypasses, `ILineChange`-derived cues); the single `shell-warning-stack` live-region owner (`App.vue:1278-1305`) is the one place transient notices announce — new title-bar/status-bar chrome may visually echo drift/stale state but must not add a second `aria-live` region; and `src/domain/anchor.ts`'s golden-hash-pinned anchor computation is read-only to the UI layer (workbench consumes `comment.anchor.line/endLine/state`, never recomputes anchor inputs).

**Major components:**
1. `WorkbenchShell.vue` — new layout host; owns the five-region slot composition (title bar / side bar / editor / bottom panel / status bar), replacing `App.vue`'s 1,000-line template without taking over its state ownership.
2. `diff-adapter.ts` (extended, not replaced) — sole Monaco-diff and multi-zone authority; keyed paired-zone map is the load-bearing data structure for every thread-state feature (resolve/reopen/reply/cross-file-nav) built on top of it.
3. `model/panel-state.ts` (new) — bottom-panel open/closed + active-tab state, intentionally separate from the existing `shellDialog` modal-state shape because "which panel tab is active, independent of open/closed" is a different state shape than "which modal is open."
4. `styles.css :root` token pipeline — single canonical geometry/color source feeding CSS, Monaco's theme, and `scripts/verify-semantic-css.mjs`'s hard-coded `CANONICAL_TOKENS` contract; every new workbench token must be added here, with at least one consumer, before any component references it.

### Critical Pitfalls

1. **Monaco view-zone height desync between Base/Head panes** — today's adapter only ever manages one zone pair at a time; many simultaneous expanded threads on independent anchors, potentially on only one side, requires a keyed per-anchor pairing model built *before* any thread-state UI is wired, or Base/Head code visibly drifts out of row alignment.
2. **View-zone DOM doesn't reliably receive pointer events** — already documented in the project's own design research (not a new discovery): buttons/textarea/resolve-reopen-delete inside a zone can silently stop responding to clicks because Monaco's mouse-handling layer intercepts above the zone. Prevention is Monaco content widgets layered over the zone via `addContentWidget`, not bare zone DOM — this needs a go/no-go spike *before* committing to the "many expanded threads" interaction model, because if content widgets don't solve it cleanly, the whole thread-rendering approach needs rethinking.
3. **Zone churn during draft reconciliation silently drops in-progress replies** — `draft-reconciliation.ts` today only ever re-renders zero-or-one zone; naive porting to multi-thread rendering would tear down and recreate every zone on every Refresh, losing scroll position and in-progress reply text. Zones must be keyed by stable `comment.id` and diffed, not rebuilt wholesale.
4. **Comment anchoring regressions via golden-hash drift** — `anchor.ts`'s `buildDurableAnchor`/`verifyDurableAnchor` is covered by a pinned golden-hash regression test; any workbench rendering change that reaches into anchor-computation inputs instead of reading already-computed fields risks silently moving the hash and regressing drift-detection correctness.
5. **App.vue decomposition silently dropping a session-kind branch** — five session kinds (committed, exact-patch, uncommitted, standalone, attached/agent-driven) have materially different shell rules (Refresh availability, pill variant, Export-tab wording); this exact failure class ("deferred to a sibling plan that never lists it") has recurred across prior milestones and needs an explicit 5-kind matrix checked off per new surface before the shell phase closes.

### Phase Ordering Rationale

- **Typecheck before structural churn, tokens before visual churn.** Both are cheap, foundational, and the cost of skipping them compounds: every `.vue` file touched during decomposition without a working typecheck gate is untyped debt; every component CSS rule written against a token that doesn't exist yet fails CI the moment it merges (`verify:semantic-css` scans the full generated CSS output, including compiled `.vue` styles — "tokenize later" just adds a guaranteed failed-CI round-trip, confirmed by both STACK.md's live reproduction and PITFALLS.md's Moderate Pitfall 5).
- **Structure before style, style before the hard engineering.** Re-plumbing existing components into new regions (Phase 21) isolates layout risk from visual risk; restyling the tree and identity/status bar (Phases 22–23) is comparatively low-risk, well-understood CSS/markup work that can absorb churn while the genuinely novel multi-zone Monaco work (Phase 24) is still being de-risked by its own go/no-go spike.
- **The riskiest phase is deliberately isolated and gated.** Comment threads (Phase 24) is the only phase ARCHITECTURE.md and PITFALLS.md both independently flag as needing a pre-build spike (pointer-event delivery) before full commitment — this is the one true go/no-go decision point in the roadmap; every other phase is "restyle/relocate with known risk," not "prove the approach works at all."
- **DESIGN.md rewrite is split, not single-phased.** FEATURES.md frames the `DESIGN.md` rewrite as a single late checklist item ("last, since should describe shipped reality, not aspiration"), while ARCHITECTURE.md's phase list bundles the token *values* into Phase 20 alongside the prose. These are reconciled, not in conflict: token **values** must land in Phase 20 (a mechanical CI-gating requirement, independent of what the shell ends up looking like), while the `DESIGN.md` **prose** describing composition/geometry is correctly deferred to Phase 26, after the shell it describes is frozen.
- **Same-wave e2e locator updates are a cross-cutting rule, not a phase.** PITFALLS.md's Minor Pitfall and the 18-05 precedent (~30 pinned Playwright locators for one rename) establish this as a discipline every phase above must follow individually — grep every `getByRole`/`getByText`/`aria-label` string match affected by that phase's rename and update it in the same commit, then re-run the full suite once per phase, not accumulate it into a separate "fix tests" phase at the end.

### Gaps to Address (Must-Resolve Items)

**1. Typecheck pairing conflict — RESOLVED, recommendation stated:**

STACK.md and ARCHITECTURE.md cite two different fixes for the same confirmed-live `ERR_PACKAGE_PATH_NOT_EXPORTED` failure (`vue-tsc` importing `typescript/lib/tsc`, a subpath TypeScript 7.0's `exports` map no longer defines):

- **Recommended — STACK.md's dual-alias scheme:** `vue-tsc@3.3.14` (confirmed via `npm view`: peer `typescript: >=5.0.0`, depends on `@vue/language-core@3.3.14`/`@volar/typescript@2.4.30`) + `typescript` devDependency aliased to `npm:@typescript/typescript6@6.0.2` (confirmed on npm registry, published by the TypeScript team's own `@typescript/` scope) + a new `@typescript/native` devDependency aliased to `npm:typescript@7.0.2` (confirmed: real native `tsc` binary, `bin: {tsc: "bin/tsc"}`). This is the scheme described directly in Microsoft's own 2026-07-08 "Announcing TypeScript 7.0" DevBlog post ("Running Side-by-Side TypeScript 6.0"). `vue-tsc@3.3.14`'s own shim-detection logic (confirmed by diffing published `vue-tsc` bundles) redirects its internal `require.resolve('typescript/lib/tsc')` call to the TS6 alias, while npm's bin-linking keys off a package's *own* `bin` field — so `node_modules/.bin/tsc` still resolves the real native TS7 binary, keeping `build:node`/`typecheck:web`'s plain `tsc` invocations at full 8–12x native speed. Only `vue-tsc`'s internal module resolution is routed through the shim. No `typescript-eslint` or other `require('typescript')` consumer exists in the repo, so the blast radius is scoped to exactly one package.
  - **Why recommended over the alternative:** first-party Microsoft authorship and an official, dated announcement vs. a third-party community package surfaced only in a closed GitHub issue comment; narrower blast radius (two officially-sanctioned aliases, each doing one job) vs. a single package that would re-route *every* `typescript` consumer through a community re-implementation; no native-binary cross-platform risk.
- **Alternative — ARCHITECTURE.md's single-package bridge:** alias `typescript` directly to `npm:typescript-native-bridge@^6.0.3-bridge` (confirmed on npm registry: currently `6.0.3-bridge.19.tsgo.7.0.2`, described as "a tsgoChecker overlay on TypeScript plus a cgo bridge (`bridge.dylib`) on typescript-go"). This was the fix suggested in closed vue-language-tools issue `#6156` pending official TS 7.1 plugin support. It is a single `devDependency` instead of two, but it is a third-party package (not Microsoft), ships a compiled native bridge artifact whose published name (`bridge.dylib`) suggests macOS-specific packaging — a cross-platform CI risk for a project targeting Node 24 LTS "cross-platform" — and has iterated through 19 published prerelease versions in rapid succession, suggesting active churn/instability relative to the stable, versioned official scheme.

**2. Reply data model — OPEN QUESTION for requirements, not decided here:**

The sketches (`comments-and-export.md`) depict a literal second message appended to the same thread (`<textarea class="reply-input">`, "Open threads get one-row reply textarea; ⌘Enter saves"), but `src/contracts/draft.ts`'s `ReviewDraftV1Schema` enforces a unique-anchor invariant via `superRefine`, and `mutate-draft.ts`'s `addComment` case rejects a second comment at an anchor already carrying one (`{ kind: 'invalidTarget' }`). This is a schema-level invariant blocking the sketched behavior, not a missing UI — it must be an explicit product/requirements decision before Phase 24 can be planned in detail:
- **Option A — relax uniqueness, add ordered thread entries.** Drop the anchor-uniqueness `superRefine`; let `addComment` append additional comments to an existing anchor; add an explicit ordering field to `WorkspaceComment`/`ReviewCommentProjection` (an existing sortable `createdAt` is already present) so a thread renders chronologically. `comment-groups.ts`'s grouping already tolerates multiple comments per file/state; only "first match" assumptions in `workspace-state.ts`/`DiffWorkspace.vue` need to change to "all matches, sorted." This touches `ReviewDraftV1Schema` and therefore requires its own schema-version bump, which **must preserve backward compatibility across export versions V1–V6** — this is a hard constraint on whichever option is chosen, not optional.
- **Option B — single comment, richer body (reply as edit-append).** Treat "reply" as literally appending text to the existing comment's `body` via the already-wired `editComment` mutation, rather than creating a second comment entity. Zero schema change, but diverges from the sketch's two-speaker-turn visual (repeated `You · 4 min ago` per reply) and loses per-reply timestamps/authorship.
- Whichever option is chosen, the resolve/reopen/delete portion of Phase 24 does **not** depend on this decision — those three actions operate on the existing single-comment-per-anchor model unchanged and can be planned/built independently of the reply-model resolution.

**3. Viewed tracking (DEFER-01) — flagged optional/separable:**

FEATURES.md identifies per-file "viewed" marking (status-bar viewed count, tree view-option, per-file "mark viewed" affordance) as depending on a **new persisted draft field** that does not exist today — unlike resolve/reopen/delete/reply, this is not pure UI work; per Loopnote's versioned-JSON persistence model, a new draft field needs the same migration discipline as any other schema change. This should be sequenced as its own small unit of backend work, not treated as a styling detail of the status bar. If this backend work slips, the rest of the shell does not need to wait on it — the status bar and tree view-option can ship with the viewed-count item visually absent or disabled rather than blocking the whole milestone (per FEATURES.md's explicit MVP sequencing note).

**4. Sketch gaps requiring product decisions before the phases that depend on them:**

All four confirmed as explicitly unresolved in the sketches themselves (`sketch-findings-loopnote`'s "Open Questions"), not research omissions:
- **Standalone-session identity pill variant** — sketch 002's state tabs cover Branches/Staged/Exact-patch but never shows what the pill looks like for a standalone file/glob session (no Base/Head at all). Blocks Phase 23's final pill spec.
- **Finish-attached-review placement** — `App.vue`'s existing `attachedFinishReady`/`finishAttachedReview` logic and the Export tab's existing readiness-checklist pattern make the Export tab a plausible inferred home, but this is inference, not a sketch decision, and must be confirmed — including how it reads for non-attached, ordinary sessions where no Finish action exists at all. Blocks Phase 25's final Export tab spec.
- **Markdown Source/Rendered toggle placement** — the existing toggle (`ActiveFileToolbar.vue`) has no stated home in the new icon-only editor title's action list (prev/next change, prev/next file, inline/side-by-side, comment nav); most likely a third icon-only toggle alongside inline/side-by-side, but the sketches don't show it. Blocks Phase 21's/22's editor-title final icon set.
- **Monaco native F7/⇧F7 Diff Review Pane and Alt+Up/Down conflicts** — Monaco's diff editor binds `F7`/`Shift+F7` by default to open its own internal Diff Review Pane overlay, and `Alt+Up`/`Alt+Down` by default to "Move Line Up/Down" — both documented Monaco defaults, both distinct from (and internal to) the app's own F7/⇧F7 change-navigation and planned ⌥↑/⌥↓ file-navigation bindings. `App.vue`'s existing `handleKeydown` already bails out for any `HTMLTextAreaElement`/`HTMLInputElement`/`HTMLSelectElement` target, and Monaco's text-input capture *is* a hidden `<textarea class="inputarea">`, so today's F7 handling only works once focus is outside Monaco's own text-input. The decision needed is explicit: should Monaco's native F7 Diff Review Pane and native Alt+Up/Down move-line action be suppressed via `editor.addAction` override in favor of the app's own navigation, or coexist? Both are implementable — this is a UX decision, not a library gap, and must be resolved before Phase 21 (document-level ⌘B/⌘J wiring) and Phase 24 (⌥F9 cycling) finalize their keybinding-ownership table, since both phases need "one layer per shortcut" to avoid the double-fire/silent-shadow failure mode PITFALLS.md documents for this exact pattern.
