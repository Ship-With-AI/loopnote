# Phase 17.1: Full Project Rename - Research

**Researched:** 2026-10-31
**Domain:** Repo-wide identifier/string rename (npm package, CLI, protocol kinds, state dirs, env vars, CSS tokens, CI/release artifacts, Supabase functions, marketplace skill), gated on a user-supplied name (D-01)
**Confidence:** HIGH (full-repo grep inventory; no new runtime dependencies)

## Summary

This phase has no new architecture to design — it renames an existing, fully-built product
(`Cumpa` / `cumpa` / `@shipwithai/cumpa`) to a name the user has not chosen yet. The work is a
classified, verifiable find-and-replace across 176 live-tree files (excluding `dist/` build
output, `.cumpa/` runtime data, and `.planning/` history, which D-11 keeps untouched), plus five
operations that cannot be scripted (GitHub repo rename, npm publish/deprecate, Supabase/Stripe
renames — D-02/D-08/D-09) that go on a manual checklist instead.

Because the name is unknown, every plan must consume a single rename-map artifact (D-01) instead
of hardcoding forms. This research inventories and classifies every occurrence so the planner can
assign each class to the correct tool (AST rename vs. verified literal replace) and the final
plan can write an automated `grep -i cumpa` exceptions-audit test per the success criteria.

## Rename Tooling

**Recommendation — two tools, dispatched by identifier class, both verified by a final audit:**

1. **AST-aware rename for TS identifiers (class 1 & 2 above)** — use `ts-morph` (already a sane
   fit: project is TypeScript/ESM, no new runtime dependency needed since `ts-morph` can run as a
   one-off `devDependency` script, not shipped). Load the project's `tsconfig.json`, call
   `sourceFile.getDescendantsOfKind(SyntaxKind.Identifier)` or simpler, `project.getSourceFiles()` +
   `renameSymbol` via the language service for each exported `CumpaIgnoreStatus`,
   `isCumpaInternalPath`, etc. This correctly updates every import/re-export site
   (`worktree-inventory.ts:12` re-exports `isCumpaInternalPath`) without manual cross-file tracking,
   and will not touch *string* occurrences (kind literals, CSS classes, env var strings) — those are
   handled by step 2.
2. **Verified literal string replace for everything else** (classes 3–8: Zod kind literals, CSS/
   token strings, env var names, `.cumpa/` path literals, `cumpa`-prefixed artifact basenames, YAML/
   Markdown/JSON/HTML prose) — a small Node script that: (a) takes the rename-map as input, (b)
   walks the file inventory (the same 176-file list, re-globbed fresh each run rather than hardcoded,
   so files added between planning and execution aren't missed), (c) does whole-word-boundary literal
   replacement per mapped string (longest-match-first, e.g. replace `cumpa.review-request` before
   bare `cumpa` so the dot isn't double-substituted), (d) reports a per-file diff count. "Verified"
   means: after replacement, re-run the `grep -i cumpa` inventory and confirm the only remaining
   hits are the allowed exceptions (below) — zero tolerance otherwise.
3. **`package-lock.json`** is excluded from manual/scripted editing — after `package.json`'s `name`
   changes, regenerate the lockfile with `npm install` (a plan task, not a text edit) so npm's own
   lockfile invariants stay intact.

## Architecture Patterns

### Pattern 1: Rename-map as the single source of truth (D-01)
All later plans consume one committed artifact (not hardcoded strings) — see
`<decisions>` D-01 in CONTEXT.md. The map must derive, from one user-supplied display name:
- Display name (e.g. `Acme`) — used in UI copy, README prose, macOS/Windows XDG path segment
  (Title-Case convention observed in `support-store.ts:60-61`)
- npm package `@shipwithai/<new>` (lowercase, URL/npm-safe)
- CLI bin command (lowercase, matches `package.json` `bin` key and `.name('cumpa')` in `run.ts`)
- Repo-local state dir `.{new}/` (lowercase, filesystem-safe)
- Linux/XDG state dir segment (lowercase, matches bin command)
- Protocol `kind` prefix (`{new}.review-request`, `{new}/export`, etc. — lowercase, dot/slash-safe)
- Env var prefix (`{NEW}_` — uppercase, underscore-safe, derived mechanically from the lowercase
  form, not asked separately)
- CSS/token prefix (`{new}-` — lowercase, hyphen-safe, matches CLI/bin convention)
- TypeScript identifier prefix (`{New}` — PascalCase, derived mechanically by capitalizing the
  display/bin form, e.g. `CumpaIgnoreStatus` → `{New}IgnoreStatus`)

A single TS/JSON constants module (e.g. `scripts/rename-map.json` or `.ts`) is cleaner than
per-file replacement tables because: (a) the literal-replace script and the AST-rename script both
read it as one input, (b) the final audit test imports the same map to build its "old string"
grep patterns, so the test can never drift from what was actually applied, (c) it is the one file
the blocking human-input checkpoint task writes, and every downstream task's `read_first` points at
it instead of re-deriving forms independently (preventing the inconsistent-derivation failure mode
CONTEXT.md's `Claude's Discretion` section leaves open).

### Pattern 2: Fresh-glob rename script, not a hardcoded 176-file list
The file inventory above is a snapshot at research time. The rename script itself must re-glob
(`grep -rliE cumpa --exclude-dir={.git,node_modules,.planning,dist,.cumpa} .`) at execution time
and operate on whatever it finds, so files touched by concurrent work between planning and
execution are still covered, and the final audit uses the identical exclusion set for consistency.
