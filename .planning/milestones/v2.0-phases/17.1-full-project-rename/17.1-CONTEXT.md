# Phase 17.1: Full Project Rename - Context

**Gathered:** 2026-10-30
**Status:** Ready for planning. **Execution blocked on the new name** (D-01).

<domain>
## Phase Boundary

Rename the product everywhere it lives in the codebase and its distribution, from Cumpa / `cumpa` / `@shipwithai/cumpa` / `.cumpa/` / `cumpa.review-request` to a new name not yet chosen. The v2.0 milestone ships **once**, under the new name, as **2.0.0**. Inserted before Phase 18 so the repositioning copy is written once, under the new name.

In scope: npm package name and `bin`, CLI command, display name in UI/CLI/docs, the repository-local state directory, the per-user XDG state directory, agent protocol `kind` values (requests and exports), code identifiers/types/CSS classes/tokens containing the name, env var names, build/release scripts and artifact names, tests, README/PRODUCT.md/docs, the marketplace skill (in the skills repo, extending Phase 17's draft PR), and a manual release checklist.

Out of scope: choosing the name (the user is still deciding), executing GitHub/npm/Supabase/Stripe operations (manual checklist only), rewriting historical records (D-11), and Phase 18 positioning copy (written under the new name afterwards).

</domain>

<decisions>
## Implementation Decisions

### Name gate
- **D-01:** **Plan with a placeholder, block execution.** Plans use `<NEW_NAME>` and derived forms, defined once in a single plan-level table: display name, npm package (`@shipwithai/<new>`), CLI command, repo-local state dir (`.<new>/`), XDG state dir name, protocol kind prefix (`<new>.review-request`, etc.), env var prefix (`<NEW>_`), CSS/token prefix, TypeScript identifier prefix (e.g. `CumpaIgnoreStatus` → `<New>IgnoreStatus`). **The first task of execution is a blocking human checkpoint** where the user supplies the name. Autonomous mode pauses there. Nothing is renamed before that.

### Distribution & compatibility
- **D-02:** **Old CLI/package: deprecate, no alias.** The new package ships only the new command. The release checklist includes a final `npm deprecate @shipwithai/cumpa "<message pointing to the new package>"` (manual). No forwarding `cumpa` bin and no shim code.
- **D-03:** **Version: the first release under the new name is 2.0.0.** There is **no** 1.7.0 under the old name: the v2.0 milestone ships once, renamed. This **amends Phase 17** D-04/D-06: the marketplace skill prerequisite becomes `<new-package> >=2.0.0 <3.0.0`, and install guidance uses the new package. Phase 17.1 updates the skill branch/draft PR that Phase 17 opened in `Ship-With-AI/skills` (skill name/path and request kinds to the new name).
- **D-04:** **Agent protocol: new kinds only.** Requests and exports use `<new>.review-request` / the new export kinds. A request with the old `cumpa.*` kind is rejected before launch with a specific error naming the new kind. V1–V3 (and the Phase 17 V4/V5) export **schemas** keep their structure, but `kind` literals change to the new prefix. Tests prove the old kind is rejected with the specific error.

### State
- **D-05:** **Repo-local `.cumpa/` is not migrated.** The new version reads and writes only `.<new>/`. Existing drafts/exports in `.cumpa/` are abandoned. Document a manual `mv .cumpa .<new>` in the README/upgrade notes. Inventory exclusion (`isCumpaInternalPath`) switches to the new dir. Researcher: decide whether the old `.cumpa/` should also stay excluded from review listings (recommended: exclude both, so old drafts never show up as reviewable files) — that is exclusion only, not migration.
  - **Amended 2026-11-02 (gap closure, 17.1-23):** do **not** document `mv .cumpa .<new>`; the renamed hash domain tags (`loopnote-*-v1`) stay, so moved drafts would not load. README upgrade notes state that 1.x drafts/exports in `.cumpa/` are not readable by 2.0.0, are excluded, and can be deleted.
- **D-06:** **Exception: the per-user supporter state is migrated.** On first run, if `<XDG_STATE_HOME or ~/.local/state>/<new>/support.json` is missing and `.../cumpa/support.json` exists, **copy** it (do not move or delete the old one), with atomic write and file mode preserved. This protects paying supporters (`src/server/support-store.ts`). It is a one-time copy, not an ongoing fallback read path.
  - **Amended 2026-11-02 (gap closure, 17.1-23):** the copied file is written with mode `0o600` (the module's convention), never the legacy file's mode.
- **D-07:** Any `.gitignore` entry Cumpa manages or recommends switches to `.<new>/`.

### Backend, env, scripts
- **D-08:** **Rename code and env vars; the live backend is manual.** In-repo identifiers, env var names (`CUMPA_SUPPORT_SERVICE_URL`, `CUMPA_RELEASE_*` → `<NEW>_...`), release/build scripts, artifact basenames, the Supabase function code and config in `supabase/`, and test fixtures are all renamed. Renaming the live Supabase project/functions, Stripe product display names and deployed secrets goes on the **manual release checklist**, not automation. The client must keep working against the existing deployed support service URL until the manual step is done (URL comes from config/env, not the name).
- **D-09:** **GitHub repo rename is a manual checklist step** (`Ship-With-AI/cumpa` → new; GitHub keeps redirects). The checklist also covers: updating `repository`/`bugs`/`homepage` in package.json (done in code, pointing at the new repo URL), git remotes, AIOS library pages, and the npm deprecation. The local folder `~/projects/diff-review` is **not** renamed.

### Scope of text replacement
- **D-10:** Rename in live code, config, tests, scripts, README, PRODUCT.md, DESIGN.md, docs/, `.claude/CLAUDE.md` project section, and the project skill in `.kimi-code/skills/` where it names the product.
- **D-11:** **History is untouched:** `.planning/milestones/**`, completed phase directories, `.planning/MILESTONES.md`/`RETROSPECTIVE.md`, and existing CHANGELOG/release-note entries keep the old name. New entries use the new name.
- **D-12:** The name story section in the README ("cumpà = friend + compare") is removed in this phase. Phase 18 writes any new name story for the new name.

### Claude's Discretion
- The order of the mechanical rename (codemod per identifier class vs per directory). Prefer AST-aware renames for TS identifiers and a verified string replace for literals, with a final `grep -i cumpa` audit that allows hits only in D-11 history paths, the old-kind rejection error, the D-06 migration source path, and the D-05 exclusion.
- How the placeholder table is stored (e.g. a single `rename-map` constant consumed by scripts/tests vs per-file replacement).

</decisions>
