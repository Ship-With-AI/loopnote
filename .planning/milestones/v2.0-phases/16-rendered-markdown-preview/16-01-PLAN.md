<objective>
Extend the existing hardened `markdown-it` renderer (`src/web/model/markdown-preview.ts`) with the four capabilities Phase 16 needs, without adding any npm dependency and without weakening its XSS/link hardening: (1) 1-indexed `data-source-start`/`data-source-end` attributes on every block type D-05 names, derived from markdown-it's `token.map`; (2) a front-matter block rule so leading `---…---` renders as a fenced YAML code block instead of misparsing into `<hr>` + a heading (D-11); (3) a task-list core rule rendering `[ ]`/`[x]` list items as disabled checkboxes (D-11, GFM); (4) an `image` **inline**-rule replacement (not a renderer-rule override) implementing D-09: relative/no-scheme image sources parse through unchanged as literal `<img src="…">` tags for the consuming component to rewrite, `http(s):` sources are replaced with the exact placeholder text from `16-UI-SPEC.md`'s Copywriting Contract, and every other scheme (`javascript:`, `data:`, `vbscript:`, etc.) still fails to parse at all (falls back to literal bracket text), exactly like `validateLink` already does for links.

Purpose: this module is the single security-hardened boundary MDV-04 depends on; RESEARCH.md's Pitfall 1 proved a renderer-rule-only `image` override never fires for relative images because the existing shared `validateLink` already blanks their `href` during **parsing**, before any `image` token exists. The fix must happen at the inline-rule level.

Output: `renderMarkdownPreview(markdown: string): string` unchanged signature, extended HTML output; `tests/unit/markdown-preview.test.ts` covering every new behavior.
</objective>

    - Block source-map stamping: for input with one heading, one paragraph, a 2-item bullet list, a 2-row table, a blockquote with one paragraph, and one fenced code block, every one of `heading_open`, `paragraph_open`, each `list_item_open`, each `tr_open` (not `th_open`/`td_open`), the blockquote's inner `paragraph_open`, and `fence` carries `data-source-start`/`data-source-end` matching the 1-indexed line span markdown-it's `.map` reports for that exact token (convert the 0-indexed end-exclusive `[start,end)` to 1-indexed inclusive via `start+1`..`end`). `table_open`/`bullet_list_open`/`blockquote_open` themselves do NOT get the attribute (D-05: anchor the row/item, not the whole table/list/quote).
    - Front matter: input beginning with a line that is exactly `---`, followed by one or more lines, followed by a line that is exactly `---`, renders as a single fenced code block (`<pre><code class="language-yaml">…</code></pre>`) containing the lines between the two `---` markers verbatim (HTML-escaped), carrying `data-source-start="1"` and `data-source-end` equal to the closing `---`'s 1-indexed line number. The rule only fires when `state.line === 0` (very start of the document); a `---` appearing later in the document (e.g. as a markdown thematic break or setext H2) renders exactly as it does today (unchanged `<hr>`/`<h2>` behavior) — add a regression case proving this.
    - Task lists: a list item whose text starts with `[ ]`, `[x]`, or `[X]` followed by at least one space renders as `<li …><input type="checkbox" disabled>` (unchecked) or `<li …><input type="checkbox" disabled checked>` (checked), with the `[ ]`/`[x]` prefix stripped from the visible text and the rest of the item text rendered normally after the checkbox. A list item that does NOT start with that pattern is completely unaffected (no checkbox, no text mutation) — add a regression case proving a plain list item in the same list stays plain.
    - Image hardening (replaces `validateLink`'s current blanket rejection of non-http(s)/mailto for images specifically): `![alt](./relative/path.png)` and `![alt](../sibling/image.svg)` (no scheme, no leading `//`) parse into a literal `<img src="./relative/path.png" alt="alt">` tag (relative src byte-for-byte unchanged, no rewriting — rewriting to the content route happens downstream in `RenderedMarkdownView.vue`, plan 16-03, not in this pure-function renderer). `![alt](https://example.test/x.png)` and `![alt](http://example.test/x.png)` never produce an `<img>` tag at all; they render the exact inert placeholder `Remote image not loaded: "alt" — https://example.test/x.png` (and the no-alt-text variant `Remote image not loaded (no alt text) — https://example.test/x.png` when `alt` is empty or absent), matching `16-UI-SPEC.md`'s Copywriting Contract exactly, wrapped in `<span class="rendered-markdown__remote-image">`. `![bad](javascript:alert(1))`, `![bad](data:image/png;base64,AAAA)`, `![bad](vbscript:msgbox(1))`, and any other non-relative non-http(s) scheme produce NO `<img>` token at all and fall back to literal bracket text `![bad](javascript:alert(1))`, exactly mirroring the existing link `validateLink` fallback-to-text behavior — add this as an explicit regression case since it is the exact failure mode RESEARCH.md Pitfall 1 documents (a renderer-rule-only fix would make this case silently do nothing instead of literal text, which is NOT a security regression but IS a behavior regression worth locking down).
    - Existing precedent tests (`renders the exact local Markdown buffer and treats hostile content as inert`, `uses the empty-state copy without persisting a rendered representation`) continue to pass byte-for-byte unchanged — run them as part of this feature's GREEN gate, do not edit their assertions.

    Override `renderer.renderer.rules.paragraph_open`, `heading_open`, `list_item_open`, `tr_open`, and `renderer.renderer.rules.fence` (capture the original `fence` rule reference first, since markdown-it's default fence renderer is a full custom function, not `self.renderToken`) to call `token.attrSet('data-source-start', String(token.map[0] + 1))` / `token.attrSet('data-source-end', String(token.map[1]))` whenever `token.map !== null`, then delegate to the original/default rendering (`self.renderToken(...)` for the `_open` rules; the captured original `fence` function, or `self.renderToken` fallback if none was registered, for `fence`). The `list_item_open` override additionally reads `token.meta?.taskChecked`: when defined, append the `<input type="checkbox" disabled{checked attr}>` HTML immediately after the rendered open-tag output, before returning.
    Replace the `image` **inline** rule itself via `renderer.inline.ruler.at('image', customImageRule)`: inside the rule, temporarily swap `state.md.validateLink` for a local image-specific validator (accepts any string NOT matching `/^[a-z][a-z0-9+.-]*:/iu` and NOT starting with `//`, i.e. relative/no-scheme, OR matching `/^https?:/iu`), delegate to markdown-it's own default `image` inline rule (imported from `markdown-it/lib/rules_inline/image.mjs`) inside a `try/finally` that restores the original `validateLink` immediately afterward (so the shared link validator used by `link_open`/`validateLink` elsewhere is never mutated for longer than this one call). Then override `renderer.renderer.rules.image` (render-time, now reachable since the token exists) to branch on the final `src` attribute: `^https?:` → emit the placeholder `<span>` using `token.attrGet('alt')`; otherwise → delegate to `self.renderToken` (literal `<img>` tag, src untouched).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Markdown source text → `renderMarkdownPreview` | Markdown source comes from repository file content (committed, uncommitted, or standalone) — not trusted; an attacker who can land a crafted file in the reviewed repository controls this input entirely |
| `renderMarkdownPreview` output HTML → DOM (via `RenderedMarkdownView.vue`, plan 16-03) | The returned string is mounted into the page DOM; it must be safe to insert without a second sanitization pass |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-------------------|
| T-16-01 | Tampering / Elevation of Privilege | `renderMarkdownPreview` — raw `<script>`/`<img onerror>` HTML in source | mitigate | `html: false` (already set, unchanged this plan); confirmed by the existing precedent test that `<script>` escapes to `&lt;script&gt;…` text, never an `html_block`/`html_inline` token |
| T-16-02 | Tampering | `renderMarkdownPreview` — `javascript:`/`data:`/`vbscript:` image sources | mitigate | new image-specific validator inside the swapped-`validateLink` inline-rule override (Priority 3b); such sources never produce an `image` token at all, falling back to literal bracket text, matching the existing link behavior |
| T-16-03 | Information Disclosure | `renderMarkdownPreview` — `http(s):` image sources | mitigate | render-time `renderer.rules.image` override replaces the token with inert placeholder text carrying no `src`/`href`; no `fetch`, no CSP-report side channel, matches D-09 exactly |
