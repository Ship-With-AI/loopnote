<objective>
Wire the web layer's standalone-session copy (D-02's exact header/state-label text) and fix a real pre-existing-pattern bug this phase's schema reuse would otherwise introduce: `App.vue`'s `:export-supported="!isUncommittedSession"` binding (`src/web/App.vue:1395`) disables the Export control whenever `'uncommitted' in session` is true — and since standalone sessions deliberately reuse that same `uncommitted` response key (Plan 15-02's Open Question 2 resolution), this binding would silently disable Export for standalone too unless corrected, directly breaking FILE-05.

Output: `IdentityHeader.vue` standalone header branch; `ActiveFileToolbar.vue`/`FileRow.vue` standalone git-state label/marker; `App.vue` `isStandaloneSession` computed and corrected `export-supported` binding.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-15-14 | Information Disclosure | `export-supported` gating | mitigate | The actual export capability is enforced server-side (`capabilities.exportReview === undefined` → 404, Plan 15-06); this client-side flag only controls button visibility, so an incorrect value here would at worst show/hide a button, never bypass the server-side 404 guard — accepted as a UI-correctness concern, not a security boundary, but still fixed because an incorrectly-hidden Export button would make FILE-05 unusable |
| T-15-15 | Tampering | Client-rendered git-state label text | accept | `standaloneGitState`/`reviewKey`/file paths are server-computed and already pass through `controlSafeDisplay` where interpolated into free text (short digest); the three D-02 label strings themselves are static literals, not interpolated from untrusted input, so no new XSS surface is introduced |
